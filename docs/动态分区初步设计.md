# 动态分区初步设计

> 状态：历史第一版设计草案；固定请求窗口方案已废弃，当前实现改为淘汰反馈控制  
> 日期：2026-09-29  
> 目标：在现有固定分区实现上，用最小改动验证动态容量比例是否值得继续研究。

本文件中的窗口需求控制实验属于历史记录。当前实现不再根据新增 KV token 占比或完成请求数更新比例，而是在实际发生淘汰后，按两类区域的淘汰 token 占比平滑调整配额。历史结果仍见 `experiments/动态分区试验/动态分区实验结论.md`。

## 1. 当前决策

第一版只引入一个新的算法变量：运行时 Agent 缓存比例 `agent_ratio`。

系统结构保持为：

```text
请求分类
  -> agent / request 两个缓存命名空间
  -> 动态调整两区容量比例
  -> 两区内部统一使用 LRU
```

当前不加入：

- Agent 专用淘汰策略；
- 跨区空闲容量借用；
- 工具返回时间或下一轮时间预测；
- 基于 TTFT 的闭环控制；
- 多指标压力评分；
- 高低水位状态机；
- Full/SWA 两套独立比例。

这一阶段只回答一个问题：**混合流量的 KV 需求随时间变化时，简单动态比例是否比固定比例更稳健。**

## 2. 与现有实现的关系

当前固定分区已经具备动态分区需要的主要基础：

- 请求已经带有 `cache_region=agent/request`；
- 区域已经进入 Radix key 命名空间；
- 两区共享物理 KV allocator；
- Classic RadixCache 已维护分区使用量和驱逐量；
- SWARadixCache 已分别维护 Full/SWA 使用量和驱逐量；
- `ensure_region_capacity()` 已能按照指定区域执行 LRU 回收；
- scheduler internal state 已能返回区域统计。

因此，第一版不修改分类、路由、Radix key 和 LRU，只把当前固定的：

```python
self.request_agent_cache_ratio
```

从启动后不变的参数改为可在运行时更新的比例。

## 3. 最小动态算法

设：

- `r_t`：当前 Agent 容量比例；
- `D_agent`：当前统计窗口内 Agent 区实际新增的去重缓存 token；
- `D_request`：当前统计窗口内普通请求区实际新增的去重缓存 token；
- `alpha`：平滑系数；
- `r_min/r_max`：Agent 比例上下限。

当前窗口的 Agent KV 需求占比为：

\[
s_t = \frac{D_{agent}}{D_{agent} + D_{request}}
\]

下一窗口比例为：

\[
r_{t+1} = \operatorname{clip}
\left(
(1-\alpha)r_t + \alpha s_t,
r_{min},
r_{max}
\right)
\]

如果一个窗口没有新增缓存 token，则保持当前比例不变。

第一版默认参数：

```text
initial_ratio = 0.61
window_requests = 64
alpha = 0.20
agent_min_ratio = 0.20
agent_max_ratio = 0.80
```

这些参数只作为实验原型默认值，不在第一轮同时进行大规模调参。为保持现有固定分区命令行兼容，代码中的 `--request-agent-cache-ratio` 默认值仍为 `0.5`；动态实验启动脚本需要显式传入 `0.61`。固定分区实验得到的 `0.61` 用作初始值，而不是作为动态控制器的长期目标。

## 4. 需求信号的定义

第一版中的 `D_agent/D_request` 使用**实际新插入 RadixCache 的去重 token 数**，不使用：

- 请求数量；
- 原始 prompt token 数；
- 命中前的输入长度；
- 预测的工具等待时间；
- 正在执行请求临时占用的全部 KV。

具体统计位置是创建真正的新 Radix 节点时：

```text
Classic RadixCache._insert_helper(): len(new_node.key)
SWARadixCache._add_new_node():       len(new_node.key)
```

节点分裂只是重新组织已有缓存，不计入新增需求。同一前缀已经存在时，匹配部分也不重复计数。

对于 SWARadixCache，同一个新节点只按其逻辑 token 长度计数一次，不把 Full 和 SWA token 相加。控制器只产生一个统一比例，再分别映射到 Full/SWA 容量。

选择这一信号的原因是它与“新增缓存保留需求”直接对应，也能避免请求数量与 KV 体积不一致的问题。它的已知限制是：写入量大但复用价值低的区域可能获得更多容量。第一轮先把这个限制作为待验证假设，不提前增加复用价值预测。

## 5. 窗口和更新时机

每次创建新缓存节点时，只累计新增 token：

```python
controller.observe_insert(region, inserted_tokens)
```

每个请求执行 `cache_finished_req()` 后，将完成请求数加一：

```python
new_ratio = controller.observe_request_finished()
```

累计完成 `window_requests` 个请求后：

1. 根据窗口内新增 token 计算 `s_t`；
2. 更新 `agent_ratio`；
3. 清空窗口计数；
4. 分别检查 Agent 和普通请求区域是否超过新配额；
5. 超额部分继续使用各区域当前的 LRU 回收。

控制器直接运行在缓存所在的调度执行路径中，不增加后台线程，也不引入新的并发修改路径。

## 6. 容量和回收语义

第一版继续采用严格分区语义：

```text
agent_quota   = total_capacity * agent_ratio
request_quota = total_capacity - agent_quota
```

某一区域超过当前配额时，只从该区域的合法候选中驱逐。另一侧即使暂时空闲，也不允许直接借用。

比例更新后，系统检查两边是否超额：

```python
self.ensure_region_capacity("agent", 0)
self.ensure_region_capacity("request", 0)
```

如果超额节点被在途请求锁定，现有 `evict()` 只能回收可驱逐部分。未完成的部分不强制终止请求，也不额外设计 pending 状态机，而是直接通过统计值计算：

```text
over_quota_tokens = max(used_tokens - capacity_tokens, 0)
```

后续请求完成、节点解锁时，再次检查两区容量并继续回收。

第一版允许由于 protected KV 出现短暂超额。这与现有固定分区“缓存保留上限而非在途请求硬截断”的语义一致。

## 7. Full/SWA 统一策略

系统始终只有一个动态比例 `agent_ratio`：

\[
Q_{agent,full}=r_t C_{full}
\]

\[
Q_{agent,swa}=r_t C_{swa}
\]

Full 和 SWA 分别检查使用量、可驱逐量和超额量，但不独立决定比例。两者的差异只属于工程执行：

```text
同一个 ratio
  -> 换算 Full 的 agent/request quota
  -> 换算 SWA 的 agent/request quota
  -> 分别执行现有区域内 LRU 回收
```

如果后续实验发现一个池长期空闲、另一个池持续成为瓶颈，再讨论是否需要不同信号或比例；第一版不增加这个自由度。

## 8. 建议的代码结构

### 8.1 新增最小控制器

建议新增：

```text
Engine/sglang/python/sglang/srt/mem_cache/request_region_quota.py
```

控制器只保存：

```python
current_ratio
initial_ratio
min_ratio
max_ratio
alpha
window_requests
window_finished_requests
window_inserted_tokens = {"agent": 0, "request": 0}
update_count
```

控制器只提供三个主要接口：

```python
observe_insert(region, num_tokens)
observe_request_finished() -> Optional[RatioUpdate]
stats() -> dict
```

它不访问 allocator，不选择淘汰节点，也不处理请求分类。

### 8.2 Classic RadixCache

需要修改：

```text
radix_cache.py
```

改动范围：

1. 初始化可选动态控制器；
2. 真正创建新节点时上报新增 token；
3. 请求完成时推进窗口；
4. 比例变化后更新 `request_agent_cache_ratio`；
5. 检查两个区域的新配额；
6. 在统计中增加当前比例和超额 token。

`evict()`、LRU 排序和区域候选过滤不修改。

### 8.3 SWARadixCache

需要修改：

```text
swa_radix_cache.py
```

与 Classic 使用同一个控制器实现和同一更新公式。比例变化后，现有 `ensure_region_capacity()` 分别按照 Full/SWA 容量换算并回收。

### 8.4 ServerArgs 和 CacheInitParams

建议增加：

```text
--request-cache-region-policy fixed|dynamic
--request-cache-ratio-window-requests 64
--request-cache-ratio-alpha 0.20
--request-cache-agent-min-ratio 0.20
--request-cache-agent-max-ratio 0.80
```

现有参数：

```text
--request-agent-cache-ratio
```

在 `fixed` 模式下表示固定比例，在 `dynamic` 模式下表示初始比例。默认策略继续为 `fixed`，避免改变已有实验行为。

## 10. 第一轮验证

### 10.1 代码级验证

至少覆盖：

1. 只有 Agent 新增 KV 时，比例平滑上升但不超过上限；
2. 只有普通请求新增 KV 时，比例平滑下降但不低于下限；
3. 两类新增 token 相同时，比例逐步接近 0.5；
4. 窗口没有新增 token 时，比例保持不变；
5. 节点分裂不重复累计 token；
6. 比例缩小时，只驱逐超额区域的节点；
7. Full/SWA 获得相同比例，但分别按照各自容量计算配额；
8. `fixed` 模式行为和当前实现保持一致。

### 10.2 实验对照

第一轮只比较：

1. 统一缓存 + LRU；
2. 固定 61/39 分区 + 区域内 LRU；
3. 简单动态分区 + 区域内 LRU；
4. 离线固定比例扫描得到的场景最优值，作为参考上界。

动态实验先使用能够确认真实类别的冻结 workload。当前 OpenHands/WildChat workload 上分类器没有产生混淆，可以先保持现有分类路径，同时在结果中明确记录分类混淆为零。

除当前 token-balanced workload 外，需要增加至少一份阶段变化 workload：

```text
阶段 1：普通请求 KV 需求占主导
阶段 2：Agent KV 需求占主导
阶段 3：恢复普通请求占主导
```

Session 内部顺序、请求内容、模型、KV 总容量和随机种子保持不变，只调整不同 Session 的到达阶段。

### 10.3 第一轮主要指标

主要看：

- 总体、Agent、普通请求 token 加权命中率；
- 动态比例随时间的轨迹；
- 两区 used/quota/over-quota；
- 两区驱逐 token；
- Full/SWA 分别的驱逐 token；
- 总体缓存利用率；
- OOM、retract 和吞吐是否退化。

TTFT 继续记录，但根据固定分区重复实验的结果，不把单次 TTFT 变化作为动态分区是否有效的主要判断依据。

## 11. 第一轮通过条件

第一版不要求动态分区在每个稳定 workload 上超过该场景单独调出的最佳固定比例。它至少需要满足：

1. 流量阶段发生变化后，比例方向正确；
2. 比例变化不会导致跨区域错误驱逐；
3. 不引入 OOM、retract 或明显吞吐损失；
4. 在阶段变化 workload 上优于固定 61/39，或者明显缩小与各阶段最佳固定比例之间的差距；
5. 比例调整产生的额外驱逐不能抵消命中收益。

如果只满足前三项而没有命中收益，说明“按新增 KV 量分配容量”的信号不够好，但动态分区执行框架仍然有效。

## 12. 根据结果迭代，而不是预先增加机制

完成第一轮后，只根据实际暴露的问题增加下一项改动：

| 观察结果 | 下一步候选改动 |
| --- | --- |
| 比例频繁来回变化 | 增大窗口或减小 `alpha` |
| 比例变化方向正确但响应过慢 | 减小窗口或增大 `alpha` |
| 写入很多但几乎不复用的区域占用过多 | 将需求信号改为带复用收益的 token 量 |
| 一侧空闲而另一侧仍大量驱逐 | 再加入最低配额以上的空闲借用 |
| 配额收缩产生大量立即重算 | 再加入限速或延迟回收 |
| Agent 在容量收缩时被 LRU 错误驱逐 | 冻结相同容量轨迹，研究 Agent 专用淘汰策略 |
| 分类错误造成会话进入错误区域 | 再评估分类器置信度和 Session 路由 |

第一轮不同时解决这些问题。每次只根据日志选择一个最主要的失败原因进行迭代。

## 13. 当前实现顺序

建议后续按以下顺序推进：

1. 实现控制器和运行时比例更新；
2. 接入 Classic RadixCache 的模拟测试；
3. 接入 SWARadixCache，并确认 Full/SWA 使用同一比例；
4. 扩展 internal state 和结构化日志；
5. 构造阶段变化 workload；
6. 先做离线/模拟检查；
7. 再运行统一、固定和动态三组真实服务实验；
8. 根据比例轨迹、驱逐量和命中结果决定第二版设计。

这份设计的核心只有“新增去重 KV token 占比的指数平滑”。其余内容用于把它安全地接入现有固定分区代码，并保证实验结果能够解释。
