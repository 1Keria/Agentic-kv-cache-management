# 混合流量下的差异化 KV 策略：方向与规划

> 日期：2026-07-29  
> 状态：**当前主规划**  
> 平台意向：SGLang（策略反馈进现有 cache / priority 接口，不重写底层 cache）  
> 数据参考：`third_party/qwen-bailian-usagetraces-anon/`、TraceLab、`lmcache_traces`、`third_party/glm-5dot1_onlinedata/`

---



---

## 要做什么（一句话）

> 同一套 LLM Serving 同时承载 **人驱动 Request 流** 与 **Agent 流**；  
> 二者对 KV 的需求不同。我们在系统层做：**提取信息区分流量 → 结合系统资源做差异化策略 → 将策略反馈进底部已有 cache 管理**。  
> **不重写底层 cache 实现**；贡献在中间的策略层。

---



## 3. 动机



### 3.1 现状

生产 Serving 往往在同一引擎 / 同一块 GPU KV 上同时吃两类流量，而不是两套隔离集群。

### 3.2 两类流量怎么区分（当前共识）

不以「有没有 session」为第一刀（Request 也可以多轮、也可以有 session）。


| 维度      | **Request（人驱动）**  | **Agent**                                |
| ------- | ----------------- | ---------------------------------------- |
| 谁推进下一跳  | **人**             | **模型 + tool 闭环**                         |
| 调用频率    | 相对稀疏（等人）          | **高频**：一步一想 → tool → 再想                  |
| 输出形态    | **长输出**（decode 重） | **短输出**（常为短文本 / tool_call）               |
| Session | 可以有，可多轮           | 通常有，且纵向前缀持续累加                            |
| 空档      | 主要等人（可很长）         | 多数为短 tool 间隙；也存在 **长间隔**（等人、慢 tool、任务间隙） |


**高频从哪来：**  
不是「一次 tool 触发多次 decode」。一次 LLM 请求 = 一次 prefill + 一次 decode；tool 在引擎外执行、本身不 decode。高频来自 agent 把任务拆成很多自动 step，轮间只等 tool、不等人，因而单位时间内 LLM 调用次数高。

**长间隔从哪来：**  
等人确认/下一条指令；慢 tool（测试、编译、远程）；任务阶段性停顿；以及排队造成的系统侧延迟。与高频短间隙可以同时存在（短间隙为主、长间隔重尾）。

### 3.3 对 KV 需求为何不同（动机核心）

- **Request**：压力偏 **长 decode 占着 KV/算力**；轮间空档不确定；请求结束后私有 KV 未来价值往往骤降。  
- **Agent**：压力偏 **短 decode + 频繁续写前缀**；短空档内 KV 很快还要用；被统一 LRU 在间隙踢掉 → 下一跳大块重 prefill，伤整条任务链。  
- **混跑时**：长生成占坑与高频 session 保活互相挤兑；**一套统一 cache 策略难以同时合理**。

因此需要的是 **差异化 KV 策略**，不是「再做一个对所有人更好的 LRU」。

## 4. 系统设想（三层闭环）

底层 Radix / 匹配 / 存取 / 引擎对 KV 的所有权 **保持不动**。我们做策略闭环：

```text
① 提取请求信息 → 区分两类流量
        ↓
② 结合「请求信息 + 当前系统资源」→ 对两类做不同策略决策
        ↓
③ 把策略结果反馈进底部已有的 cache 管理（soft signal）
```



### 4.1 提取 / 区分

从请求（及可选的显式标注）中抽出足以判断流量类别与状态的信息。  
候选信号（待收敛为最小集合，非最终字段表）：

- 显式：`traffic_class` / agent 标记 / `session_id`
- 行为：是否 tool 环、历史调用间隔、输出长度分布、轮次密度
- 状态：active / tool-wait / human-idle / closed（策略可见即可）

原则：优先 **client/router 显式标签**（故事更硬）；纯推断可作为辅助或消融。

### 4.2 策略（系统贡献的核心）

输入：

- 流量类别与 session 状态（来自 ①）
- **当前系统资源**：KV 水位、并发、正在进行的长 decode、活跃 agent session 数等

输出：对两类流量的 **不同管理决策**，例如：

- 保谁 / 压谁（相对优先级）
- 空档期间降权快慢（短 tool-wait vs 长 human-idle）
- 两类流量的容量预算 / 公平性约束（避免保 A 死 B）

策略必须是 **资源感知** 的：同样是 agent，KV 近满与空闲时决策应不同。

### 4.3 反馈进底部 cache

将 ② 的决策写成引擎 **已经吃得懂** 的接口，例如：

- priority / 保留偏置
- 衰减 / TTL 类提示（若基线支持）
- 其他现有 soft hint（以具体引擎版本为准）

约束：

- **不**重写 Radix、**不**自建第二套物理 cache、**不**绕过引擎所有权；
- hint 可被引擎拒绝时，行为仍安全（降级为基线策略）。

## 5. 明确不做


| 项                           | 处理                                              |
| --------------------------- | ----------------------------------------------- |
| 重写底层 cache / 独立 pinned 生命周期 | **不做**（与 SGLang 演进方向也不合）                        |
| 假装拥有生产全局到达时间线               | **不做**；跨 session 交错若需实验，须显式合成并写明（见 `真实数据构造.md`） |

---



## 6. 评测应长什么样（方向级，细节后补）

- **负载**：人驱动长输出 trace + agent 高频短调用 trace **混跑**（比例可扫）  
- **基线**：统一策略（如全局 LRU / 不区分类别的 priority）  
- **本系统**：①②③ 闭环后的 class-aware 策略  
- **指标（双边都要报）**  
  - Agent：TTFT、重 prefill / avoided prefill、session 连续性相关指标  
  - Request：TPOT、尾延迟、吞吐  
  - 全局：goodput / 公平性，禁止「只优一类」

数据原材料可继续用：百炼、TraceLab、`lmcache_traces`。  
**最终实验数据 = 按本规划构造出来的混合负载**（见 §7 D0），不是原材料本身。

## 7. Roadmap



### 7.0 首先做什么（已对齐）

**最重要的是先造出一份能用的混合负载数据（基础），再用原版 Serving 跑一遍，从实测里分析问题是什么，再决定怎么处理。**

```text
造数据（D0）
  → 原版 vanilla 跑通并落盘（D1）
  → 从数据诊断痛点（D2）
  → 再设计差异化策略怎么处理（D3 → ①②③）
```

不先凭假设锁字段和策略公式。旧教训是 **机制先于问题**；现在反过来：**数据与基线痛点先于策略**。

百炼 / TraceLab / lmcache 是 **原材料**；最终数据 = 带类别标签、可复现的 **Request∪Agent 混合负载**。

---



### 7.1 分阶段路线图


| 阶段     | 名称            | 要回答的问题                       | 主要产出                     | 退出条件（Go）                       |
| ------ | ------------- | ---------------------------- | ------------------------ | ------------------------------ |
| **D0** | **造混合数据**     | 能否构造可复现的 Request∪Agent 混跑负载？ | 负载配方 + 生成脚本/落盘 + 类别标签    | 可重复生成；两类可辨；比例/到达/水位可扫          |
| **D1** | **原版基线实测**    | 统一 cache 策略下混跑会发生什么？         | vanilla 跑次 JSON/报告（双边指标） | 跑通、可复现；Agent/Request/全局指标齐全    |
| **D2** | **问题诊断**      | 数据里暴露的核心冲突是什么？               | 痛点笔记（现象→假说→与资源水位关系）      | 能一句话说清「统一策略败在哪」；可被策略针对         |
| **D3** | **处理方案**      | 针对 D2，①②③ 最小策略是什么？           | 信息集 + 策略变量 + 反馈接口草案      | 每条对策对准 D2；不改 cache 内核          |
| **D4** | **策略原型 + 对照** | 反馈后痛点是否缓解且不单边崩？              | 原型 + 与 D1 对照             | 相对 vanilla 双边可解释改善或明确 tradeoff |
| **D5** | **主实验与论文**    | 扫参/消融/叙事是否够顶会？               | 实验矩阵 + 主表                | claim 清晰、基线公平                  |


依赖：

```text
D0 → D1 → D2 → D3 → D4 → D5
造数据 → 原版跑 → 分析问题 → 再谈怎么处理
```

---



### 7.2 各阶段注意点

- **D0（当前第一优先）**  
  - 拼法可继承 `真实数据构造.md`：Session 内真；跨 Session 交错显式合成。  
  - 必须带 **类别标签**（Request vs Agent）。  
  - 先 **小而可复现**，不求一上来全量生产形状。
- **D1**  
  - 原版 = 不区分类别的现有策略；同一负载、固定种子；先不接我们的反馈环。
- **D2**  
  - 从 D1 曲线/分位数读问题；若打脸两类定义，改定义后回到 D0 迭代。
- **D3 之后**  
  - 才进入「提取 → 策略 → 反馈」；设计必须 **对准 D2 痛点**。

## 8. 状态机式总结

```text
目标：顶会系统论文
问题：同一 Serving 上 Request（人·长输出）与 Agent（短输出·高频，兼有长空档）KV 需求冲突
方法：提取区分 → 资源感知差异化策略 → soft 反馈现有 cache
约束：不改底部 cache 内核
当下：先造混合数据（D0）→ 原版跑（D1）→ 从数据诊断（D2）→ 再谈怎么处理
```

本文是接下来讨论与实现的 **唯一方向锚点**；D0 配方细节可另开短文档，优先级以本节为准。
