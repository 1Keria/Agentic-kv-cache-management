# 请求分类模型特征预算实验

## 结论

模型判断请求属于 `agent_like` 还是普通 `request`，输出
`q_agent = P(agent_like | request features)`。本轮实验重新扫描所有派生 workload，按底层
来源去重，并修正了 GLM 的分组：`trace_id` 是单次调用，不能作为会话组；GLM 使用 workload
保留的推断 `session_id`。同时重新检查了 GLM 的语义标签，发现 GLM 流量不是天然全为 agent。

最终建议：

1. 不把 `n_system_messages` 当作 agent 的语义定义；它只是当前数据中的强模板信号。
2. 在 GLM 完整语义审计完成前，不把 1 维规则作为生产真值判定器；2 维 `has_tools + n_system_messages` 仅作为当前分布下的候选。
3. 4 维作为需要更丰富结构信号时的稳健扩展；8/12 维没有带来准确率增益。
4. 16 维只保留作消融或校准实验，不建议作为默认模型。它在留出 GLM 上漏掉 19 条 agent 请求。

## 数据边界

真正的原始来源只有三类：

| 来源 | 标签 | 去重后记录 | 来源组 |
| --- | --- | ---: | ---: |
| `third_party/glm-5dot1_onlinedata` | 16,553 agent-like + 6 request | 16,559 | 9,690 |
| `third_party/skillsbench` | `agent`/`openhands`，agent-like | 7,737 | 181 |
| `third_party/wildchat` | `request` | 42,296 | 21,295 |
| **合计** |  | **66,592** | **31,166** |

GLM 中确认的 6 条普通请求对应原始 source 行号 `1355`、`1520`、`1696`、`1749`、`1750`
和 `1848`。它们的任务分别是股票估值、劳动仲裁、银行合规自查、鸡舍设计图片、化工事故
案例和行政票据制度；消息中没有工具定义或工具调用。标签修正规则保存在
`models/request_classifier/labels.py`，缓存中的最终标签统计为 agent-like `24,290`、普通
request `42,302`。

`workloads/` 下的 36 个 `workload.jsonl` 是上述来源的比例扫描、混合、截断和评测派生物，
不是 36 个独立数据集。扫描到的派生行数为 134,629，去重键为：

```text
source identity + call/turn position + max_tokens + prompt_body
```

来源组规则为：GLM 使用 `session_id`，SkillsBench 使用 trajectory `source.path`，WildChat
使用 `conversation_hash`。这样同一底层轨迹不会同时出现在训练和测试中。

## 输入特征

输入只使用请求到达时可见的 `prompt_body` 和 `max_tokens`，不读取原始文本词汇。完整 16 维
候选见 `models/request_classifier/features.py`，包括工具结构、消息角色计数、内容长度和
输出预算。长度类使用 `log1p`，再用训练集均值和标准差标准化。

### 字段含义

| 特征 | 含义 | 原始计算 |
| --- | --- | --- |
| `has_tools` | 请求是否提供工具定义 | `tools` 非空为 1，否则为 0 |
| `log_tool_count` | 工具定义数量的规模 | `log1p(len(tools))` |
| `log_tool_schema_chars` | 工具 schema 的结构规模，不读取 schema 词汇 | 对紧凑 JSON 序列化后的 `tools` 字符数取 `log1p` |
| `log_message_count` | 上下文消息总量 | `log1p(len(messages))` |
| `n_system_messages` | system 角色消息数量 | 原始计数 |
| `n_user_messages` | user 角色消息数量 | 原始计数 |
| `n_assistant_messages` | assistant 角色消息数量 | 原始计数 |
| `n_tool_messages` | tool 角色消息数量 | 原始计数 |
| `n_function_messages` | function 角色消息数量 | 原始计数 |
| `log_tool_call_count` | assistant 消息中的 `tool_calls` 数量 | `log1p(所有 tool_calls 数量)` |
| `has_tool_role` | 是否出现 tool 角色消息 | `n_tool_messages > 0` 为 1 |
| `has_tool_calls` | 是否出现工具调用结构 | `tool_calls` 或旧格式 `function_call` 存在为 1 |
| `log_content_chars` | 所有消息 content 的总字符规模 | 递归统计文本/结构化 content 后取 `log1p` |
| `log_system_chars` | system 消息 content 的字符规模 | system content 字符数取 `log1p` |
| `log_tool_message_chars` | tool 消息 content 的字符规模 | tool content 字符数取 `log1p` |
| `log_max_tokens` | 客户端输出 token 预算的规模 | `log1p(max_tokens)` |

其中 `log1p(x) = log(1+x)`，用于压缩长尾数值。`log_tool_call_count` 只统计
`tool_calls` 数组；旧格式 `function_call` 会影响 `has_tool_calls`，但不会增加该计数。
所有字符数只统计长度，不把具体文本内容输入模型。

### `n_system_messages` 能否单独判断类别

在修正 GLM 这 6 条普通请求后，当前去重数据中可以观察到非常强的经验规则：

```text
n_system_messages > 0  =>  agent_like
n_system_messages == 0 =>  request
```

该规则在 66,592 条记录上按修正后的标签达到 `100%`；这是当前数据构造和已知标签的结果，
不是通用协议保证。普通聊天可以带 system，agent 也可以把 system 指令转成 user/developer
或放进服务端模板。2 维模型加入 `has_tools` 后只是增加结构冗余，不能消除标签语义问题。

最终采用的特征组合遵循嵌套预算：

| 维度 | 特征组合 |
| ---: | --- |
| 1 | `n_system_messages` |
| 2 | `has_tools`, `n_system_messages` |
| 4 | `has_tools`, `log_message_count`, `n_system_messages`, `n_tool_messages` |
| 8 | 4 维 + `log_tool_count`, `log_tool_schema_chars`, `log_tool_call_count`, `log_content_chars` |
| 12 | 8 维 + `has_tool_calls`, `log_system_chars`, `log_tool_message_chars`, `log_max_tokens` |
| 16 | 12 维 + `n_user_messages`, `n_assistant_messages`, `n_function_messages`, `has_tool_role` |

## 评估协议

- 分层来源组切分：60% train、20% validation、20% grouped test，`seed=42`。
- 特征选择只使用 validation；随后用 GLM/SkillsBench 留一来源，并加入未参与训练的 WildChat
  负类请求做联合测试。
- 模型为 `budget -> 32 -> 16 -> 1` 的 MLP，ReLU、Dropout `0.05`，带正类权重 BCE，
  阈值 `q_agent >= 0.5`。
- 训练设备为 `cuda:0`，NVIDIA H100 80GB HBM3。

修正标签后的 Grouped test 包含 12,842 条记录。下表的 GLM 指标在全部 16,559 条 GLM

记录上计算，WildChat 全部 42,296 条记录均正确判为普通 request。

| 1 | 100.0000% | 100.0000% | 100.0000% | 100.0000% | 100.0000% |

| 4 | 99.9844% | 99.9557% | 99.9879% | 99.9879% | 100.0000% |

### 选择建议

- **当前数据的最低延迟方案：1 维 `log_system_chars`。** 它在两种测试上均为 100%，但它
  仍然是 system 模板信号，不能被解释为通用 Agent 身份证明。
- **推荐实验默认：4 维。** 它在当前验收中与 1/2 维同样准确，同时保留工具和消息结构冗余，
  对 system 模板轻微变化更有缓冲空间。
- **不推荐默认使用 8/12/16 维。** 当前数据没有带来收益，反而在跨来源测试中出现误报或漏报。
- 以上结论受 GLM 标签审计完整性限制；在加入新的普通应用 system 请求或新的 Agent 协议前，
  不应把 100% 当成线上泛化保证。

另外单独验证了一个不含任何 system 特征的 4 维候选：
`has_tools`、`log_tool_count`、`has_tool_calls`、`log_content_chars`。它在同一跨来源协议上达到
99.9952%（41,588/41,590，漏掉 2 条 Agent），略低于 system-heavy 4 维，但不会把
`n_system_messages` 直接当作身份依据。若线上协议不能保证 system 模板稳定，应优先考虑这个
system-free 候选，并配合 `unknown`/低置信度状态。

系统第一版实际接入的 checkpoint 已按该 system-free 4 维组合重新用全部去重数据拟合并保存：

```text
models/request_classifier/checkpoints/final_system_free/budget_4/request_classifier.pt
```
该文件仅使用 `has_tools`、`log_tool_count`、`has_tool_calls`、`log_content_chars`，在线加载器会
拒绝包含 `n_system_messages` 等不可用特征的旧 checkpoint。

反事实压力测试见 `models/request_classifier/checkpoints/feature_budget_counterfactual.json`：
给普通请求添加一个 32 字符中性 system 后，2/4 维分别有 100% 的普通请求被翻为 Agent；
删除 Agent 的 system 后，1/2 维分别漏掉 100% 的 Agent。这说明原始数据上的满分主要依赖
当前协议模板，不能解释为任意线上请求的身份识别能力。

## 限制

- GLM 是混合真实流量，不能仅凭来源名推断 agent；本轮只修正了已人工核查的 6 条普通 GLM
  请求，仍需要更完整的人工/规则审计来发现潜在遗漏。
- 三类原始来源的标签定义决定了实验只能验证 agent-like 与普通 request 的二分类，不能证明
  对未知的第三类流量同样有效。
- WildChat 是唯一普通请求来源；留出普通来源会导致训练集没有负类，因此联合测试采用“留出
  agent 来源 + 未见 WildChat 负类”的协议。
- GLM 已参与特征选择，后续论文或独立报告仍应冻结特征后收集全新的 agent 来源做最终测试。
