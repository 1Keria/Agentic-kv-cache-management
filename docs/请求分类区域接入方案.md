# 请求分类区域接入方案

## 本轮已确认的决策

1. **同一 Session 的处理**：线上请求无法可靠携带“Agent/普通”身份时，仍对每个到达请求运行分类器；显式 Session 在首个成功请求确定区域后保持粘性，后续请求不因单次预测变化而切换区域。这样同时保留了无客户端标签时的判断能力和会话前缀连续性。Session 关闭并重新创建后重新分类。
2. **严格隔离**：暂时接受一侧空闲而另一侧不足时的容量浪费，不实现跨区域借用或共享公共前缀。
3. **固定分区验收**：冻结分类阈值 `0.5` 和同一份混合 workload，先通过离线扫描选择 Agent 缓存容量比例，再配对比较统一缓存实验和固定分区实验；流量组成只作为 workload 条件，不直接决定容量比例。
4. **观测指标**：第一轮先通过 scheduler internal-state 记录区域容量、占用、驱逐和回放侧 TTFT/hit 指标；确认口径后再接 Prometheus，不让指标接入改变首轮基线。

## 当前基线

第一版只验证“按请求身份隔离 KV 缓存”这一件事：

- 请求入口由 tokenizer 进程执行 system-free 4 维分类器；
- 分类器输出 `agent` 或 `request`，结果写入内部 `cache_region`；
- `Req` 将区域加入 Radix key 命名空间，因此两个区域不共享前缀；
- 两个区域使用同一个物理 KV allocator，但各自有固定的 token 容量上限；
- 区域内部继续使用原有 LRU，暂不引入动态权重、reuse predictor 或借用机制。

这里的“容量”指 **RadixCache 中已经提交的缓存 token**。正在执行请求的 KV 属于
protected/in-flight 状态，调度必须优先保证请求完成，因此在高并发或分块预填充期间可能
短暂超过配额；请求释放锁后会立即按该区域的 LRU 回收超额节点。也就是说，比例是缓存
保留上限，不是对单个请求的硬截断，也不是 GPU 全部瞬时占用的精确分账。

当前 checkpoint：

```text
models/request_classifier/checkpoints/final_system_free/budget_4/request_classifier.pt
```

输入特征为：

```text
has_tools, log_tool_count, has_tool_calls, log_content_chars
```

模型只读取请求体的结构和长度，不读取标签、来源、session、到达时间或文本词汇。
该 checkpoint 在 66,592 条去重样本上阈值 0.5 的拟合集结果为 accuracy 99.9970%，漏掉 2 条
Agent、误报 0 条；这不是未知线上流量的泛化保证，仍需在真实流量回放中复验。

## 固定比例

比例按 **KV token 容量** 定义，而不是请求数量：

```text
Agent 区域容量 = Agent 缓存容量比例 × KV 缓存总容量
普通请求区域容量 = (1 - Agent 缓存容量比例) × KV 缓存总容量
```

本轮不预先指定固定比例。先在冻结 workload 上离线扫描候选比例，根据统一口径选择表现最好的
Agent 缓存容量比例，再用该比例执行唯一一次固定分区 GPU 回放。当前去重数据中 Agent 约占
36.5% 的请求数，但 `log_content_chars` 反变换后的内容字符量约占 87.6%；这说明请求数比例和
KV 压力比例可能完全不同，也不应直接把任一流量比例当作缓存容量配置。

## 严格隔离语义

当某一区域超过自己的 token 配额时，只从该区域的可驱逐叶节点中按 LRU 驱逐；另一侧
即使有空闲缓存，也不会被该区域直接占用。这样可以明确测量区域隔离的收益和容量浪费，
后续再单独实现“保留最低配额 + 空闲容量借用”。

当前实现通过区域命名空间禁止跨区域前缀命中。这会重复缓存相同的公共前缀，属于有意的
第一版基线；后续若重复开销明显，再设计 shared/public trunk，而不是在本阶段隐式混用归属。

区域配额只对 classic `RadixCache` 的普通 prefill/decode 分配路径做了严格接入。启用
speculative decoding 或其他后端时，启动阶段会明确拒绝，避免额外分配路径绕过配额；分块
预填充和会话缓存仍需在后续验证中单独检查。对于显式 Session，分类器仍对每个到达请求运行
用于观测，但缓存路由采用首次成功请求的区域并在会话内保持粘性；后续请求与首次分类不同
时只记录 debug 日志，不切换缓存命名空间。这样不依赖客户端提供身份标签，也避免同一会话
在两个区域之间反复 miss。关闭并重新创建 Session 后重新分类。

## 启动参数

```bash
--enable-request-cache-regions \
--request-classifier-checkpoint models/request_classifier/checkpoints/final_system_free/budget_4/request_classifier.pt \
--request-agent-cache-ratio 0.5 \
--request-classifier-threshold 0.5
```

当前区域配额接入的是 classic `RadixCache`。Unified、SWA、Mamba、C++ 和其他后端会在
启用开关时明确报不支持，避免出现“分类生效但配额没有生效”的假实验。

## 必须观测的指标

实验至少记录：

- 每区域 used/evictable KV tokens；
- 每区域驱逐次数和驱逐 token 数；
- 每区域请求数、分类概率与分类耗时；
- 每区域 prefix hit tokens、命中率和 TTFT；
- 总体 KV 利用率，以及是否存在长期空闲或持续不足的区域。

当前实现先通过 scheduler 的 internal-state 暴露区域容量、占用和驱逐累计值，足够支撑第一轮
配对回放；确认指标口径后再接入 Prometheus，避免在基线实验中同时引入新的采集开销和标签维度。

## 后续决策点

1. 先在冻结 workload 上离线扫描并选出 Agent 缓存容量比例，再运行固定分区实验。
2. 如果一侧长期空闲，再评估借用机制；借用会改变实验解释，不能和第一版基线混在一起。
3. 如果公共前缀重复占用明显，再评估共享树和公共 trunk；需要重新定义节点归属和计费。
4. 线上出现低置信度样本后，再增加 `unknown` 区域或保守路由；当前两区域版本保持二分类，避免隐藏错误。
5. V4 Flash 使用 `SWARadixCache`，当前已按同一 Agent 容量比例同时划分
   Full KV 池和滑动窗口 KV 池；Unified/Mamba/C++ 后端仍不在本轮范围。

## 固定分区验收协议

本阶段先冻结分类阈值和流量数据，只离线选择 Agent 缓存容量比例：

- 分类阈值 `0.5`；
- workload、到达时间、随机种子、模型、KV 总容量和调度参数全部固定。

快速验证使用：

```text
experiments/固定分区试验对比/data/token_balanced_openhands_wildchat/workload.jsonl
```

这份 workload 只包含 OpenHands 和 WildChat，GLM 完整保留给后续真实线上流量测试。数据不是按
调用次数配平，而是使用已有 DeepSeek V4 Flash 真实重放返回的 `prompt_tokens`，按每个 Session
最后一轮的 prompt token 近似其最终 KV 上下文压力：

- OpenHands：7 个 Session、211 次调用，最终 prompt token 合计 385,107；
- 普通请求：548 个 Session、1,050 次调用，最终 prompt token 合计 385,107；
- 总计：555 个 Session、1,261 次调用；
- 两类最终上下文 token 差值为 0；
- 6 个混合波次覆盖 30 分钟，Session 内等待最多 30 秒；
- 每次输出最多 256 token，prompt 内容和 Session 边界不变。

因此，调用次数明显不均衡是有意设计：固定分区按 KV token 容量划分，不按请求次数划分。数据的
选择规则、DeepSeek V4 token 记录来源和文件哈希都保存在同目录的 `spec.json` 与 `manifest.json`。
当前 4 维分类器在这份冻结 workload 上将 211 个 OpenHands 调用全部判断为 Agent、1,050 个
WildChat 调用全部判断为普通请求；这一结果只说明当前快速验证数据上的路由没有分类混淆，不能
替代后续 GLM 线上测试。

使用同一份 workload 做配对对照：

| 配置 | 区域开关 | 目的 |
| --- | --- | --- |
| 统一缓存实验 | 关闭 `--enable-request-cache-regions` | 原始统一 RadixCache 基线 |
| 固定分区实验 | 开启区域，使用离线选出的 Agent 缓存容量比例 | 验证静态最优分区的收益空间 |

两个配置必须使用相同的请求顺序和到达时间。主要结论看总体 TTFT、prefill token、吞吐、OOM/
retract；同时按 Agent/request 分别看 prefix hit tokens、命中率、TTFT、区域 used/evictable
tokens 和驱逐 token。回放时保留 workload 的真实类别只用于离线核对分类混淆，不直接替代线上分类器
做路由。

流量组成和 Agent 缓存容量比例是两个独立变量。本轮先在同一份冻结 workload 上通过离线模拟
选择一个固定的 Agent 缓存容量比例，再只进行两次完整 GPU 回放：原始统一缓存和选定比例的固定
分区。该比例只代表这份流量上的静态最优点；后续动态分区负责在线估计和调整比例。

### 当前目录的运行入口

脚本不再依赖固定的旧工作目录。默认从当前仓库定位代码；如环境中的 Python、模型或 `sglang`
路径不同，使用环境变量覆盖：

```bash
MIX_REPLAY_PYTHON=/path/to/python \
  bash experiments/固定分区试验对比/scripts/replay_workload.sh

SGLANG_BIN=/path/to/sglang MODEL_PATH=/path/to/deepseek-v4-flash \
  bash scripts/shell/v4flash.sh
```

启动统一缓存实验时保持 `ENABLE_REQUEST_CACHE_REGIONS=0`（默认）；启动固定分区实验时使用：

```bash
ENABLE_REQUEST_CACHE_REGIONS=1 \
REQUEST_CLASSIFIER_CHECKPOINT=models/request_classifier/checkpoints/final_system_free/budget_4/request_classifier.pt \
REQUEST_CLASSIFIER_THRESHOLD=0.5 \
REQUEST_AGENT_CACHE_RATIO=<离线选出的 Agent 缓存容量比例> \
  bash scripts/shell/v4flash.sh
```

两次启动只切换区域开关，模型、TP、KV 总容量和其他参数保持完全一致。

## 本阶段建议的验收顺序

1. 关闭 speculative decoding，使用 V4 Flash 实际选中的 `SWARadixCache`
   验证区域命名空间、区域内 LRU 和 Full/SWA 双池 token 配额；确认两侧
   不会互相命中或互相驱逐。
2. 按固定分区验收协议配对运行统一缓存实验和固定分区实验，记录区域命中率、驱逐 token、
   TTFT、总体利用率和 OOM/回收失败次数；阈值固定为 0.5。
3. 先单独检查 session 的首次分类/粘性继承和分块预填充的额外 KV 分配点；speculative
   decoding 在完成配额接入前会被启动检查拒绝，不把未覆盖路径的结果与第一版基线混合比较。
4. 线上分类异常默认按 `request` 保守处理，并记录异常计数；只有确认异常率和误分类代价后，
   才考虑 `unknown` 区域或动态借用。
