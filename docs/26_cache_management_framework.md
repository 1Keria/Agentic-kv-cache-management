# Cache 管理：从单一驱逐策略到全链 Agent-Aware 重设计

> 日期: 2026-06-30
> 背景: 在 `docs/25_research_directions.md` 讨论基础上，确认后续工作总主题为"适合 agent 场景的 KV cache 管理方式"
> 起点: 用户直觉——"一定有更好的管理方式适合 agent 场景"，且驱逐策略只是其中一环

---

## 0. 核心立场

后续工作围绕 **cache 的管理** 展开，不局限于驱逐策略。驱逐是 cache 管理链上的**末端环节**（容量满才触发），把工作钉死在驱逐一个点，既低估了问题，也撑不起顶会范围。一个完整的 agent-aware cache 管理系统应该在 cache 生命周期的多个环节做对，让驱逐尽量少发生，而不是把驱逐策略做得多精巧。

---

## 1. 判据统一：复用价值是根

### 1.1 关键判断

讨论中确认的核心直觉：**如果能找到一个 cache 的"复用价值"作为统一评判标准，其他管理问题会自然消解**——能被复用的前缀自然价值更高，该留的留下、该走的走。

这意味着方向一不是"设计多个独立机制"，而是"**把一个判据定义对，并让它贯穿 cache 管理的每个决策点**"。

### 1.2 为什么复用价值能统一其他维度

之前讨论的几个候选管理方式（A/B/C），最终都收敛到 C：

- **A（以 session 为单位管理）**：不需要主动做。因为一个 block 属于哪个 session、session 还活着吗，这些信息最终都会**反映在复用价值里**。活 session 的骨干 prefix 会被反复 lookup，价值高；死 session 的 block 不再被 lookup，价值归零。价值信号把生命周期信息**编码进去了**，不用显式跟踪 session。
- **B（确定性共享 vs 概率性复用分层）**：不需要主动分。L0 价值稳定地高（所有 session 都复用），L1_unique 价值随 session 起伏——分层是价值分布的自然结果，不是先验分类。

→ C（复用价值判据）是根，A 和 B 是 C 成立后自然涌现的结论。

### 1.3 命门：复用价值是"回看"还是"前看"

C 能不能真的统一掉 A/B，取决于复用价值怎么做：

| 类型 | 判据 | 对生命周期敏感度 | 风险 |
|------|------|----------------|------|
| **回看（backward）** | 历史复用频率推断未来 | 滞后 | session 刚结束时 L1_unique 历史频率仍高，但未来价值已归零 → 误判保护该驱逐的 |
| **前看（forward）** | 预测未来会不会被复用 | 实时 | 需要感知"当前依赖结构"，不靠历史频率 |

- **前看型可行** → C 是根，A/B 被吸收，核心机制是"基于依赖结构的前看复用价值判据"，是真正的新管理方式
- **只能回看型** → C 退化成 frequency-based LRU 变体，动态性滞后，必须靠 A 补 session 生命周期信息，C 统一不了 A

### 1.4 候选的前看型信号（待验证）

前看型判据若成立，应该能从**当前/近未来的依赖结构**推断复用价值，而非历史频率：

- **当前依赖数**：一个 block 现在被多少个活跃请求的 lookup 依赖（多个 session 的 prefix 都经过它 → 短期必复用）
- **骨干属性**：一个 block 是不是某个正在 prefill 的请求的已计算 prefix（正在生成的 turn 的骨干 → 后续 turn 必复用）

这些信号看的是**当前和近未来**，不是历史，天然具备动态性。

### 1.5 验证实验（最靠前的工作）

命门问题**可以测**，不需要现在拍：

- 拿 agent trace 离线算每个 block 的"未来 N turn 内被复用次数"（理想前看价值）
- 分别算"历史频率"（回看信号）和"当前依赖结构"（前看信号）与理想值的相关性
- 哪个信号跟未来复用相关性高，就走哪条路

## 2. Cache 管理是一条链，不是单点

一个 KV cache 从产生到消失，经过多个环节，驱逐只是其中末端一环：

```
1. 注册/写入    block 第一次产生 → 进 cache index
2. 查找/命中    新请求来 → 在 index 里找已有 prefix
3. 跨层移动     GPU ⇄ CPU ⇄ SSD 三级 offload / load_back
4. 容量决策     不够用时 → 驱逐谁、抢占谁（驱逐策略在这）
5. 生命周期     什么时候让一个 block 彻底失效
```

> ⚠️ **事实校正（2026-06-30 源码确认）**：跨层移动是**三级**架构，不是两级。vLLM 和 SGLang 都支持 SSD/disk 作为第三层 KV cache：
> - **vLLM**：GPU → CPU(primary) → SSD(secondary)，`FileSystemTierManager`（`vllm/v1/kv_offload/tiering/fs/manager.py:62`，`O_DIRECT` 写磁盘），`TieringOffloadingManager`（`manager.py:111`）编排三级 cascade/promotion。已实现 + 单测 + 官方文档，非 experimental。
> - **SGLang**：L1(GPU) → L2(CPU) → L3(storage)，`HiCacheFile`（`hicache_storage.py:319`）+ `LRUFileEvictor`，生产可走 nixl(GDS)/3FS/mooncake。比 vLLM 更成熟。
> - **易混点**：vLLM 的 `cpu_offload_gb` 是模型权重 UVA offload，与 KV cache 的 CPU/SSD tier 完全无关。P6 测的 load=0 是 KV cache 的 CPU 层。
> - **实测空白**：我们 P6 只测了 GPU↔CPU 两级（load=0）。CPU↔SSD 之间是否也有独立 LRU 不协调，**完全未测**——这是待补的实验（见 §5）。

### 2.1 已测痛点其实已横跨 4 个环节

之前一直把 P1/P2/P5/P6 当独立痛点看，串成链后发现它们散落在不同环节：

| 环节 | 已测痛点 | 本质问题 |
|------|---------|---------|
| 1. 注册/写入 | P5（block 对齐浪费 ~15 tok）、SGLang 匹配边界 50 tok/turn | 注册粒度/时机 |
| 2. 查找/命中 | P1（并发共享失效）、方向二（同批不可见） | 查找时机/可见性 |
| 3. 跨层移动 | P6（GPU↔CPU offload load=0，双层独立 LRU）；CPU↔SSD 未测 | 三级架构，跨层管理不统一 |
| 4. 容量决策 | P2（驱逐 L0）、S4（统一树也保不住） | 驱逐判据 |
| 5. 生命周期 | 尚未直接测，P4（增长 3.64×）间接相关 | block 何时该死 |

### 2.2 每个环节在 agent 场景下都有特有管理问题

**环节 1：注册/写入**
- 现在**被动注册**：prefill 算完才写 index。但 agent 的 L0/L1_shared 是**可预知的确定性内容**，为什么等 prefill 完成才注册？→ 接回方向二的 eager registration。注册时机本身是管理问题。

**环节 2：查找/命中**
- 现在按 **block hash 链式匹配**，遇内容发散点全 miss。但 agent prefix 有语义层级（L0/L1/L2），能否**按层级匹配**而非按 hash 链？比如先 O(1) 查 L0 在不在，再往下匹配 L1——和链式 hash 不同的查找结构。

**环节 3：跨层移动（备份）**
- ⚠️ **源码核实更正**：offload store **不是"舍弃"，是"备份"**。store 之后 block **仍在 GPU**，store 只是"顺便在 CPU/SSD 存一份副本"。store 决定"CPU/SSD 有没有副本"，和"block 从 GPU 消失"（驱逐，环节 4）是**两条独立路径，不联动**。
  - store 触发于每步调度对**活 request** 的 prompt 段（`offload_prompt_only` 跳过 decode、`store_threshold` 过滤一次性 prefix）；GPU→CPU 完成后无条件 cascade 到 SSD
  - 驱逐（环节 4）不触发 store，也不检查是否已备份——`_maybe_evict_cached_block` 全程不调 connector（`BlockPool` 类无 connector 字段）
- **三级架构各级独立淘汰，互不通知**：GPU LRU、CPU LRU/ARC、SSD 无淘汰（靠 hash 文件名去重）；CPU 淘汰也不 cascade 到 SSD（直接 `del`/移 ghost）。和 P6 的 GPU/CPU 独立 LRU 是同一类问题在 CPU↔SSD 上的延续。
- agent 场景下**该备份什么、沉到哪一层有讲究**：
  - L0（全员共享、几乎永不用）理论上该沉到 SSD，GPU 留给活跃 session
  - 活 session 的 L1_unique/L2（短期会复用）该留 GPU
  - 死 session 的该直接丢弃，别占 CPU/SSD
- 系统分不清 → offload 形同虚设（GPU↔CPU load=0，P6）。跨层不只是"统一 index"结构问题，还有"备份什么、沉到哪一层"的决策问题，以及"备份↔舍弃不联动"的问题。
- ⚠️ **实测空白**：P6 只覆盖 GPU↔CPU 两级。CPU↔SSD 之间是否也独立 LRU 互不协调（vLLM 的 FS 层靠 hash 去重无显式淘汰；SGLang 的 L3 是独立 `LRUFileEvictor`），**尚未测量**。若成立，则"三级 cache 各自为政、无统一判据"的论点更强。

**环节 4：容量决策（驱逐/舍弃）**
- ⚠️ **源码核实更正**：在 GPU 上，"舍弃"（block 从 GPU 消失）**只有驱逐这一条路**。offload store（环节 3）不是舍弃。
  - 驱逐 = `_maybe_evict_cached_block` 删 hash + reset_hash，纯 LRU 顺序，无价值跳过分支
  - **驱逐和备份不联动**：驱逐不触发 store，被驱逐的 block 有没有 CPU 副本**无保证**（三种结局：store 已完成可恢复 / store in-flight 被 flush 真丢 / 根本没 store 真丢）
- 见 §1，复用价值判据。但环节 3 和 4 联动看：**备份和舍弃各干各的，都不看价值**——该备份的（高价值、即将被驱逐的）可能没备份就被扔了（P2 真丢），备份了的可能是死 session 的垃圾（垃圾滞留），备份到 CPU/SSD 后三层各自淘汰、找不回（P6）。三个问题同根：**备份和舍弃不联动，且都不看价值**。

**环节 5：生命周期**
- 现在 block **无显式生命周期**，靠 LRU 间接淘汰（"最久未用"≈"该死了"）。但 agent 的 block 有**明确失效时机**：session 结束，它的 L1_unique/L2 立刻全部失效。系统不知道 session 结束 → 死 session 的垃圾 block 滞留 cache，挤占活 session 空间，甚至被误判高价值保护。**这是 LRU 在 agent 场景下最隐蔽的浪费，尚未测量。**

## 3. 串成链后的认知变化

### 3.1 驱逐不是最关键问题

如果前面环节（注册、生命周期）做对，走到驱逐时 cache 里该留的留着、该走的早走，驱逐压力小很多。现在所有问题堆到驱逐爆发，是因为**前面环节失管**。好的 cache 管理系统应该**让驱逐尽量少发生**，而不是驱逐策略多精巧。

### 3.2 环节联动

- 环节 5（生命周期）做对 → session 结束立刻回收 L1_unique → 环节 4（驱逐）压力降半，环节 3（offload）不用搬死 session 垃圾
- 环节 1（eager 注册）做对 → 环节 2（查找）并发不可见顺带解决

→ 印证 §1 直觉：找到核心判据（复用价值），很多问题自然解。因为复用价值在链的**每个环节都能用**：注册时预判价值、查找时按价值排序、offload 时按价值搬、驱逐时按价值留、生命周期按价值归零。

### 3.3 方向一范围应扩展

之前方向一局限在 P2+P6（驱逐+跨层）。若主题是"agent-aware cache 管理"，P1（查找）、P5（注册粒度）、未测的环节 5（生命周期）都可纳入。

→ 方向一从"驱逐策略改进"扩展成"**贯穿 cache 管理全链的 agent-aware 重设计**"。这个范围才配得上顶会，单一驱逐策略撑不起。

---

## 4. 范围扩大的纪律：必须保留统一核心

链上 5 个环节都能做，不代表都要做。顶会最忌"什么都改一点，什么都没改透"。若方向一变成"5 个环节各提一个机制"，会成松散工程拼盘，无统一核心。

**纪律**：即便范围扩大，必须保留**复用价值**这一个统一判据贯穿全链。所有环节改进都应是"让 cache 管理的每个决策点都用上复用价值判据"，而非"每环节各搞各的"。

→ 这样扩展才有凝聚力：不是 5 个独立改进，是 **1 个判据在 5 个环节的应用**。

## 5. 当前未定的问题

1. **复用价值是回看还是前看**（§1.3）—— 决定 C 能否统一 A/B，是方向一从直觉变可做机制的关键分叉。需先做 §1.5 验证实验。
2. **工作范围是横向扩全链，还是纵向钉死驱逐做深** —— 横向扩成全链 agent-aware cache 管理（范围大，需统一判据压住）；纵向钉死驱逐一个环节做透（范围小，深度够）。两种都能发，路径不同。
3. **环节 5（生命周期）是否真的存在可测浪费** —— "死 session 垃圾 block 滞留"目前是推断，需实测确认是否值得做成独立机制。
4. **CPU↔SSD 跨层是否也有独立 LRU 不协调（待补实验）** —— P6 只测了 GPU↔CPU（load=0），三级架构的第三层 SSD 完全未测。需确认：vLLM/SGLang 的 CPU↔SSD 之间是否独立淘汰、查找是否回查 SSD。若成立，"三级各自为政"论点强化方向一的判据统一卖点。
5. **eager registration（环节 1）是否纳入方向一** —— 还是保留在方向二作为独立主线。若方向一扩成全链，eager registration 自然属于环节 1，方向二可能被吸收。
