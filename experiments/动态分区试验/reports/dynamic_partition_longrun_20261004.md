# 动态分区长期优化记录（2026-10-04）

本轮目标是检查两个候选方向：在 allocator fallback 时延迟补标 stale surplus，
以及用最低保障加共享池消除固定 61/39 比例依赖。Full 与 SWA 始终使用同一套区域
规则，只分别执行物理容量核算和回收。

## 延迟补标候选

在 4 个 Agent session、2 条普通热链、`mem_fraction_static=0.35`、串行阶段回放
（普通预热 → Agent 压力 → 普通回访）中，`borrow_lazy_reclass` 与 `borrow` 完全一致：

| 策略 | 总体命中率 | Agent | 普通请求 | Full/SWA 驱逐 token | 回访首条命中 |
|---|---:|---:|---:|---:|---:|
| borrow | 32.6415% | 32.0662% | 61.9644% | 167,936 / 903,168 | 0 / 0 |
| borrow_lazy_reclass | 32.6415% | 32.0662% | 61.9644% | 167,936 / 903,168 | 0 / 0 |

两种模式均完成 72/72 请求。该 workload 中 fallback 仍然发生，但延迟补标没有产生
额外可复用前缀，因此保留为诊断对照，不进入正式策略。

## 比例无关的 elastic 候选

`elastic` 为 Agent 和普通请求各保留 20% 最低保障，剩余 60% 作为共享池；软回收线
只由当前 resident mix 裁剪到 20%～80%，不把流量比例写入硬配额。

在同一阶段 workload 上，单次结果为：

| 策略 | 总体命中率 | Agent | 普通请求 | Full/SWA 驱逐 token | TTFT p50 |
|---|---:|---:|---:|---:|---:|
| borrow（61/39） | 32.6415% | 32.0662% | 61.9644% | 167,936 / 903,168 | 912.9 ms |
| elastic（20/20 + 共享池） | **33.4985%** | **32.9400%** | 61.9644% | 408,064 / 891,392 | 730.5 ms |

在 128 请求稳定串行扫描中，elastic 使用初始比例 0.61 和 0.50 的结果逐项相同，
且与 borrow 的命中率相同：总体 78.9395%、Agent 84.3625%、普通请求 49.2865%。
这证明实际容量规则不依赖离线的初始 61/39 比例。

历史大阶段 workload 中 elastic 曾低于 borrow，说明共享池会把更多容量让给当前占用
较高的一侧，Agent 工作集长期占满时可能牺牲保护强度。因此它目前是有潜力的比例无关
候选，尚不足以替换正式 `borrow` 默认。

## 长阶段切换验证

使用完整 mixed workload（1261 请求，`mem_fraction_static=0.45`）和普通→Agent→普通
阶段 workload（1261 请求，`max_inflight=16`）验证了共享池软线的时间滞后。瞬时软线
在阶段切换时会立即把共享池交给 Agent，普通回访前缀因此损失；固定步长的软线移动
可以保留一部分对侧工作集，同时在交错流量中继续适配。

| workload / 配置 | 总体命中率 | Agent | 普通请求 | TTFT p50 | Full/SWA 驱逐 token |
|---|---:|---:|---:|---:|---:|
| mixed，borrow（61/39） | 88.9485% | 93.5882% | 39.2616% | 686.4 ms | 661248 / 796416 |
| mixed，elastic 瞬时 | 90.4758% | 95.1576% | 40.3373% | 601.1 ms | 280320 / 661248 |
| mixed，elastic `soft_step=0.05` | 88.7906% | 93.3653% | 39.7995% | 728.0 ms | 371456 / 811520 |
| mixed，elastic `soft_step=0.10` | **90.6050%** | **95.1608%** | **41.8163%** | **598.5 ms** | **297728 / 650496** |
| mixed，elastic `soft_step=0.20` | 90.4184% | 95.0101% | 41.2449% | 700.4 ms | 322816 / 662528 |
| 阶段，borrow（61/39） | 89.7724% | 95.0823% | 32.9085% | 406.4 ms | 321024 / 725248 |
| 阶段，elastic 瞬时 | 88.9887% | 94.6837% | 28.0008% | 423.8 ms | 513280 / 794880 |
| 阶段，elastic `soft_step=0.05` | **89.6002%** | **95.1576%** | **30.0849%** | 431.0 ms | 457984 / 739072 |
| 阶段，elastic `soft_step=0.10` | 89.2672% | 94.9348% | 28.5723% | 413.9 ms | 414208 / 768256 |
| 阶段，elastic `soft_step=0.20` | 89.5313% | **95.1922%** | 28.9084% | **413.8 ms** | 429824 / 744448 |

阶段 workload 的单次运行仍有调度噪声，因此不能据此宣称 elastic 已经超过 borrow；但
`soft_step` 明确解决了瞬时 elastic 的阶段切换退化。`pressure_first` 作为对照会把
普通回访提高到 35.1518%，却把 Agent 命中率降到 91.1744%，总体只有 86.7351%，不适合
作为统一回收顺序。

## 代码与验证

- 新增 `request_cache_elastic_reclaim_order`：保留原 `request_first`，并提供
  `pressure_first` 对照；Full/SWA 使用同一个区域顺序。
- 新增 `request_cache_elastic_soft_step`：默认 1.0 表示瞬时 resident-mix 软线；实验中
  推荐从 0.10 起步，较小值提供阶段切换滞后。
- 软线状态、目标值和回收顺序都写入 `server_info`，可通过轨迹复查。
- Classic/SWA 区域单元测试 **60 项通过**；`py_compile`、`bash -n` 和 `git diff --check`
  通过。

当前正式默认仍是 `borrow`。elastic 的 `soft_step=0.10` 是跨两类 workload 最有希望的
实验配置，但在重复阶段实验确认稳定性前，不改变正式默认。

## Tail-first 与近期活动门控（2026-10-04）

在 elastic 的共享池中，Full 和 SWA 使用同一个区域方向；当物理池即将满且一侧低于
最低保障时，把该方向上方共享层的较新尾部节点置为优先回收候选，保留较早的历史链。
`request_cache_elastic_activity_window` 是一个局部、在线的安全门控：只有最低保障不足
的一侧在最近 N 次分类请求内访问过，才启用这次 tail-first。它不预测工具返回时间、turn
长度或离线流量比例；设为 0 时退化为无门控版本。

短阶段负载的两次成对回放结果如下，命中率完全一致，但活动门控显著减少无效回收：

| 配置 | 总体命中率 | Agent | 普通请求 | tail-first 回收调用 | Agent SWA 回收 token |
|---|---:|---:|---:|---:|---:|
| borrow | 32.6415% | 32.0662% | 61.9644% | — | — |
| elastic，window=0 | 35.4734% | 34.9537% | 61.9644% | 70 | 406,016 |
| elastic，window=32 | 35.4734% | 34.9537% | 61.9644% | 21 | 92,160 |

在 256 请求 mixed 负载上，三次成对回放的 elastic 总体命中率分别为 79.15%、80.00% 和
80.14%，对应 borrow 为 78.44%、78.33% 和 78.25%。Agent 命中率分别为 86.18%、87.81%
和 87.45%，均高于对应 borrow；普通请求收益在 38.18%～41.49% 之间，受到调度顺序影响
明显。因此这里的结论是收益方向稳定，单次百分点不能脱离回放方差解读。

在 1,261 请求长 mixed 回放（`mem_fraction_static=0.45`）中：

| 策略 | 总体 | Agent | 普通请求 | TTFT p50 | TTFT 均值 | 缓存 token |
|---|---:|---:|---:|---:|---:|---:|
| borrow | 90.2231% | 94.6742% | 42.5559% | 657.1 ms | 1,213.8 ms | 8,045,568 |
| elastic，window=32 | **90.5246%** | **95.1922%** | 40.5390% | 662.3 ms | **1,150.9 ms** | **8,072,448** |

这一轮 elastic 多缓存 26,880 token，总体提高 0.30 个百分点、Agent 提高 0.52 个百分点，
普通请求下降 2.02 个百分点。它适合 Agent 占主导且需要共享池的压力场景；若普通请求的
服务下限更重要，应继续使用 `borrow` 或单独提高最低保障再做容量扫描。

当前推荐的实验参数为：`request_cache_region_policy=elastic`、最低保障 `0.2/0.2`、
`request_cache_elastic_soft_step=0.10`、`request_cache_elastic_activity_window=32`。
这仍是研究候选，正式默认保持 `borrow`。前一轮 Full/SWA 区域测试共 **65 项通过**，并通过
`py_compile` 与 `git diff --check`。

## 连续运行保护的长程复核与候选淘汰

随后把 activity window 与同类连续运行长度同时作为在线活动判定。这样在一个阶段已经
持续较久、另一侧刚切入时，保留原始 61/39 返回保障；两侧近期交错时仍允许 20/20
最低保障加共享池。Full 与 SWA 使用同一个活动状态和软线。

在相同 1,261 请求 mixed workload、`mem_fraction_static=0.45`、`soft_step=0.10` 下，
窗口 32 的新回放为：总体命中率 **90.4815%**、Agent **95.0917%**、普通请求
**41.1104%**、shadow 额外重算 **22,016 token**、TTFT p50 762.2 ms。相同代码下
窗口 16 降为 90.4557%/95.1576%/40.1020%，shadow 额外重算升至 24,320 token；
缩短窗口没有带来收益，因此保留 32。

阶段切换 workload（普通 → Agent → 普通，`max_inflight=16`）进一步说明窗口不能任意
缩短：窗口 16 的总体/Agent/普通命中率为 88.6385%/93.7546%/33.8497%，shadow
额外重算 185,344 token；窗口 32 为 90.1198%/95.1922%/35.7994%，shadow 额外重算
54,016 token。窗口 32 同时保持 Agent 侧 shadow 额外重算为 0。

还对两个机制候选做了完整回放：

| 候选 | workload | 总体 | Agent | 普通请求 | shadow 额外重算 | 结论 |
|---|---|---:|---:|---:|---:|---|
| stale-tail-first | 阶段 | 89.7667% | 95.1859% | 31.7320% | 85,504 | 淘汰；长期不活跃侧的最新尾部仍可能是回访工作集 |
| pressure-adaptive soft line | mixed | 89.8959% | 94.4608% | 41.0096% | 74,240 | 淘汰；resident mix 偏向长 Agent 上下文，压力修正没有改善软线 |

因此当前可复现的研究候选是 `elastic + soft_step=0.10 + activity_window=32 +
连续运行保护 + request_first`。它在 mixed 压力回放中比同轮 borrow 多缓存 136,704 token，
shadow 额外重算少 136,192 token；在阶段切换中也超过同轮 borrow；但 TTFT 和普通
请求的单次结果仍受并发完成顺序影响，不能据此替换正式默认。`borrow` 继续作为正式基线，
elastic 作为后续动态分区论文对照。

本轮最终检查：Full/SWA 区域单元测试 **67 项通过**，`py_compile` 和 `git diff --check`
通过；失败的候选服务进程均已退出。shadow 指标仍只覆盖输入前缀，混合 workload 没有真实
生成 token ID，coverage gap 需要在报告中保留。

## 后续候选复核（2026-10-04）

为避免把请求冷启动误判为空闲，新增了 `request_cache_elastic_activity_requires_hit` 对照。
在 `scan_mixed_256`、`mem_fraction_static=0.35`、`window=32` 下，命中门控将总体命中率降到
48.2109%，Agent 降到 56.3268%，普通请求降到 4.7068%；同一 trace、同一参数但采用原始
活动判定时为 60.1883%/70.0183%/7.4960%。原因是大量首次请求没有前缀命中，普通区域
不再刷新在线活动，elastic 共享池长期偏向 Agent。shadow 额外重算也从 193,024 token
升到 304,640 token，其中 Agent 从 139,776 升到 247,296，普通请求从 53,248 升到
57,344。该参数保留为负向诊断，默认继续关闭。

还测试了三个机制方向：

| 候选 | workload | 总体 | Agent | 普通请求 | 结论 |
|---|---|---:|---:|---:|---|
| one-sided hard return reserve | 阶段切换 | 89.7552% | 95.1576% | 31.9001% | 冷启动和阶段回收过于保守，淘汰 |
| hard reserve（含冷启动保护） | 阶段切换 | 89.4825% | 94.8563% | 31.9337% | 初始 61/39 限制共享池，淘汰 |
| `activity_first` | 阶段切换 | 90.0193% | 95.0760% | 35.8666% | 与现有候选在波动范围内 |
| `activity_first` | 持续混合 | 90.4011% | 95.1105% | 39.9675% | 低于现有候选，淘汰 |

因此代码中不保留上述 hard reserve 和 `activity_first` 分支。当前最小且可复现的研究候选仍是
`elastic + soft_step=0.10 + activity_window=32 + request_first`；它在同一轮持续混合回放中为
90.4815%/95.0917%/41.1104%，阶段切换为 90.1198%/95.1922%/35.7994%。后续若继续优化，
应优先从回收粒度或准入证据入手，并以 shadow 额外重算 token 作为主要诊断，避免继续增加
依赖 workload 预测的比例控制器。
