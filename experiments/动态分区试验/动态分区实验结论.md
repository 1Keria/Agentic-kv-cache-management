# 动态分区实验结论（历史窗口控制器）

> 本文记录固定请求窗口版本的实验结果。当前代码已改为淘汰反馈驱动的动态控制器，本文不代表当前实现。

## 结论

当前“按窗口内新增 KV token 占比连续调整严格分区比例”的方案不适合作为正式设计。

它可以在边界清晰的阶段流量中通过激进参数取得收益，但同一参数在持续混合流量中明显退化；减慢控制器或限制比例范围也不能同时解决这两个场景。问题不只是参数没有调好，而是当前信号和执行语义存在结构性错配：新增写入量不等于缓存价值，比例缩小时立即驱逐，而随后扩大比例无法恢复已经删除的 KV。

下一版应保留两类请求分区和区内统一 LRU，将动态分区改成更简单的“固定保障 + 空闲容量借用”：两区保留固定容量保障，一侧空闲时另一侧可以借用；保障区重新产生需求且共享池超额时，只回收对方借用的部分。这样在持续混合流量下退化为已经验证过的固定 61/39，在阶段流量下又能利用暂时空闲的容量，不需要预测工具时间、turn 返回时间或连续比例控制器。

## 实验设置

- 模型：DeepSeek-V4-Flash；
- GPU：8 张 H800；
- 缓存：Full/SWA 使用同一分区策略，区内均为 LRU；
- workload：555 个 session、1,261 个请求、8,917,410 个 prompt token；
- Agent：7 个 OpenHands session、211 个 turn；
- 普通请求：548 个 session、1,050 个 turn；
- 随机种子：42；
- CUDA Graph：关闭；
- 所有受控运行固定生成 16 token，避免生成阶段掩盖缓存机制；
- 每组均为 1,261/1,261 请求成功，0 错误；
- 同一 workload 内各策略的 prompt、请求顺序、模型、缓存容量和服务参数一致。

两种流量形态：

1. `mixed_scaled`：保持原混合波次顺序，将 1,800 秒到达时间线压缩到 180 秒；
2. `request_agent_request`：将 session 到达重排为普通请求主导、Agent 主导、普通请求主导三个阶段，session 内 turn 顺序和 prompt 不变。

动态参数：

| 版本 | 窗口 | alpha | Agent 比例范围 |
|---|---:|---:|---:|
| 默认 | 64 | 0.2 | 0.2～0.8 |
| 快响应 | 16 | 0.5 | 0.2～0.8 |
| 窄弹性带 | 16 | 0.5 | 0.5～0.7 |

## 核心结果

### 持续混合流量

| 策略 | 总体命中率 | Agent 命中率 | 普通请求命中率 | cached token | 相对固定分区的总体变化 |
|---|---:|---:|---:|---:|---:|
| 固定 61/39 | **88.6787%** | **93.4721%** | 37.3456% | **7,907,840** | - |
| 默认动态 | 88.4346% | 93.0232% | **39.2953%** | 7,886,080 | -0.2441 pp |
| 快响应动态 | 86.6174% | 91.1556% | 38.0179% | 7,724,032 | -2.0613 pp |
| 窄弹性带动态 | 84.0079% | 88.2364% | 38.7238% | 7,491,328 | -4.6708 pp |

默认动态只把部分收益从 Agent 转移给普通请求：普通请求命中率提高 1.9497 个百分点，但 Agent 命中率下降 0.4489 个百分点。由于 Agent prompt token 占比和单次复用价值更高，最终少命中 21,760 token。

加快控制器后，比例在 0.2～0.8 之间频繁摆动，Agent Full KV 累计驱逐量从固定分区的 392,192 增至 569,856 token，总体少命中 183,808 token。把范围限制到 0.5～0.7 仍未解决问题，Agent Full KV 累计驱逐量进一步升到 799,488 token，总体少命中 416,512 token。

### 普通请求 → Agent → 普通请求阶段流量

| 策略 | 总体命中率 | Agent 命中率 | 普通请求命中率 | cached token | 相对固定分区的总体变化 |
|---|---:|---:|---:|---:|---:|
| 固定 61/39 | 87.1399% | **93.8111%** | 15.6979% | 7,770,624 | - |
| 默认动态 | 83.8672% | 88.0764% | **38.7910%** | 7,478,784 | -3.2727 pp |
| 快响应动态 | **88.7964%** | 93.7514% | 35.7321% | **7,918,336** | **+1.6565 pp** |
| 窄弹性带动态 | 86.9304% | 92.4394% | 27.9336% | 7,751,936 | -0.2095 pp |

默认参数先在普通请求阶段把 Agent 比例压到 0.2，Agent 阶段开始后又需要多个 64 请求窗口才能恢复。结果是 Agent 命中率下降 5.7347 个百分点，虽然普通请求命中率提高 23.0931 个百分点，仍净少命中 291,840 token。

快响应参数能够及时完成阶段切换：相对固定分区，Agent 命中率只下降 0.0597 个百分点，普通请求命中率提高 20.0342 个百分点，净多命中 147,712 token。但该参数在持续混合流量中又少命中 183,808 token，因此不能作为统一配置。

## 从轨迹得到的原因

### 1. 新增 KV 写入量不是容量价值

控制器当前估计的是“最近由哪一类写入了更多新页”，而真正需要优化的是“下一段时间保留哪一类 KV 能减少更多重算”。Agent 前缀一旦保留，后续长上下文可以多次复用；普通请求写入量大，不代表这些页具有同等的未来复用价值。

### 2. 完成请求窗口会混入调度反馈

窗口按完成请求计数。当前 workload 中 Agent 只有 7 个长 session，而普通请求有 548 个 session。窗口组成同时受请求长度、并发和缓存命中影响，并不只是外部流量比例。缓存策略改变完成顺序后，控制信号本身也会改变。

### 3. 比例缩小造成不可逆损失

每次比例更新后立即按照新配额回收。比例随后回升时，只增加空配额，已经驱逐的 KV 不会恢复。因此一次短窗口噪声可以制造长期重算损失。

单个 TP rank 对应的比例总变差为：

| 场景 | 默认 | 快响应 | 窄弹性带 |
|---|---:|---:|---:|
| 持续混合 | 0.797 | 5.001 | 2.038 |
| 阶段切换 | 1.308 | 3.139 | 1.301 |

窄弹性带虽然限制了绝对范围，但小窗口仍会反复在边界之间切换，所以只限制 `min/max` 不能消除驱逐抖动。

### 4. 同一组参数无法覆盖两种形态

- 慢控制器在持续混合流量中接近固定分区，但跟不上阶段切换；
- 快控制器能跟上阶段切换，但在持续混合流量中频繁重新分区；
- 限幅后两边都没有取得稳定正收益。

这说明继续搜索 `window/alpha/min/max` 最多找到某个 workload 的局部最优，不能解决 workload 依赖问题。

## 下一版最小方案

采用 work-conserving 的“固定保障 + 借用”即可，不再连续预测目标比例：

1. Agent 和普通请求分别保留 61% 和 39% 的保障份额；
2. 某一区域实际占用低于保障份额时，空闲部分可被另一侧使用；
3. 借用页仍属于借用方，并继续使用该区域的 LRU；
4. 原所有者再次需要容量且共享池超额时，优先回收对方借用的页，直到恢复保障份额；不因单侧超过基础份额就提前回收；
5. 两区都持续有压力时，系统自然退化为固定 61/39；
6. Full/SWA 继续使用同一规则，只分别执行容量核算和回收。

完整 workload 的后续复核表明，高低水位主动回收会在共享池尚未超额时提前删除可复用前缀。`mixed_scaled` 上总体命中率由 `87.6509%` 提升到 `89.2959%`，`request_agent_request` 上由 `88.0844%` 提升到 `89.1811%`；因此实现默认关闭主动水位回收（`high=0`、`low=0`），正水位只保留给显式实验。

另外，borrowed-only 回收现在严格限制在 borrowed 节点及其 borrowed 父链内；删除 borrowed 叶子后不会把受保障父节点重新加入同一候选集合。这个修复属于缓存所有权和树结构维护，不改变 LRU 或容量控制算法。

该方案只改变容量可用性，不增加 Agent 专用淘汰算法，不依赖工具时间预测，也不需要窗口、alpha、比例上下限等控制参数。它直接对应本轮实验显示的两类需求：持续混合时保护固定分区收益，阶段切换时利用暂时空闲容量。

## 跨界页修复后的最终复核

旧实现只在“插入前已经超过保障份额”时标记 borrowed。一个新缓存页从保障份额内跨到份额外时，该页会被错误地当作受保障内容，后续归还容量时只能触及其他节点。当前实现按缓存节点粒度处理跨界页：只要插入后超过本区保障份额，且对侧仍有真实空闲保障容量，就把该页记为 borrowed。这个改动不引入请求窗口、预测时间或自定义收益函数，仍然是固定保障份额、空闲借用和区内 LRU。

在相同的 `mixed_scaled`、1,261 个请求、固定 16 token 输出和 `high=low=0` 下，修复后的最终复核结果如下：

| 策略 | 总体命中率 | Agent 命中率 | 普通请求命中率 | cached token | Full/SWA 驱逐 token |
|---|---:|---:|---:|---:|---:|
| fixed 61/39 | 87.1428% | 91.7363% | 37.9507% | 7,770,880 | 877,056 / 961,024 |
| borrow | **88.8021%** | **93.2366%** | **41.3121%** | **7,918,848** | **678,144 / 811,008** |

相对固定分区，borrow 总体提高 1.6593 个百分点，Agent 提高 1.5003 个百分点，普通请求提高 3.3614 个百分点；Full 和 SWA 驱逐量分别减少 22.7% 和 15.6%。borrow 期间记录到的归还原因全部是 `global_overage`，没有主动高低水位回收。两种策略均为 1,261/1,261 请求成功、0 错误。

在同样参数下的 `request_agent_request` 阶段切换 workload 中，fixed 的总体、Agent、普通请求命中率分别为 `86.2069%`、`92.4017%`、`19.8661%`，borrow 分别为 `88.0356%`、`92.6968%`、`38.1187%`。borrow 让普通请求重新使用阶段性空闲的 Agent 保障之外容量，同时 Agent 命中率基本不变；这验证了“需求回来时归还 borrowed 页”的机制在阶段切换下有效。

这说明当前阶段应继续保留“固定保障 + 空闲容量借用”作为动态分区基线。下一步优先检查更高压力、不同保障比例和阶段切换 workload 下的稳定性；暂不增加基于时间预测、窗口平滑或收益估计的控制器。完整机器可读结果位于 `experiments/动态分区试验/results/latest_20260930/mixed_scaled_boundary_fix/`。

## 精确新增页回收修复后的复核

前面的部分实验还存在一个分配层问题：分区预留已经按实际新增页计算，但 paged allocator 随后仍按“每个请求都新增一页”估算全局回收量。这个过估计会在请求复用当前页时额外删除缓存，而且这次回收不带请求区域归属，容易抵消借用策略的收益。

当前实现改为在 prefill 和 decode 中都使用 allocator 实际需要的新增页数。Full/SWA 仍使用同一个区域规则，只分别统计各自物理池。新增回归单测覆盖了“多请求中只有部分请求跨页”和“decode 不跨页”的情况，区域单测共 `25 passed`。

在相同的 0.45 静态缓存容量、61/39 保障份额和固定 16 token 输出下，完整混合流量结果为：

| 策略 | 总体命中率 | Agent 命中率 | 普通请求命中率 | cached token | Full/SWA 驱逐 token |
|---|---:|---:|---:|---:|---:|
| fixed | 89.7409% | 94.5236% | 38.5221% | 8,002,560 | 673,792 / 727,552 |
| borrow | **90.4758%** | **95.0603%** | **41.3793%** | **8,068,096** | **504,576 / 663,296** |

borrow 相对 fixed 提高 `0.7350 pp` 总体命中率，Agent 提高 `0.5367 pp`，普通请求提高 `2.8572 pp`；Full/SWA 驱逐分别减少 `25.1%` 和 `8.8%`。阶段切换流量中，borrow 相对 fixed 提高 `2.7147 pp` 总体命中率，Agent 提高 `0.2449 pp`，普通请求提高 `25.3789 pp`，Full/SWA 驱逐分别减少 `26.1%` 和 `28.4%`。

因此，之前完整混合流量中 borrow 接近持平或略低的主要原因是分配层过量回收，而不是 Full 与 SWA 需要两套策略，也不是动态借用本身没有价值。修复后持续混合和阶段切换都保持正收益，但收益大小仍取决于两类 token 的构成：当前 workload 中 Agent prompt token 约占 `91.4%`，普通请求命中率的大幅改善会被总体 token 加权稀释。新结果和原始日志位于 `experiments/动态分区试验/results/diagnosis_20261001_exactpages/`。

## 当前代码无水位最终复核

前述 exactpages 结果来自 borrowed 计数修复之前的运行，其中 mixed borrow 的
`swa_cached_borrowed_tokens` 曾出现负数。该目录保留作为历史诊断，不再作为最终证据。
在当前代码上重新运行相同的 1,261 请求 workload，使用 `mem_fraction_static=0.45`、
Agent 61% / 普通请求 39%、固定 16 token 输出，并关闭主动水位回收
（`high=0`、`low=0`），结果如下：

| workload | 策略 | 总体命中率 | Agent 命中率 | 普通请求命中率 | cached token | 墙钟秒 |
|---|---|---:|---:|---:|---:|---:|
| mixed_scaled | fixed | 89.3590% | 94.1249% | 38.3204% | 7,968,512 | 348.677 |
| mixed_scaled | borrow | **90.3810%** | **95.1576%** | **39.2280%** | **8,059,648** | **348.167** |
| request → Agent → request | fixed | 87.2892% | **93.7357%** | 18.2526% | 7,783,936 | 380.581 |
| request → Agent → request | borrow | **89.2758%** | 93.7294% | **41.5810%** | **7,961,088** | **379.680** |

在 mixed workload 中，borrow 相对 fixed 提高 `1.0220 pp` 总体命中率、
`1.0337 pp` Agent 命中率和 `0.9076 pp` 普通请求命中率。阶段切换 workload 中，
总体提高 `1.9866 pp`，Agent 变化为 `-0.0063 pp`，普通请求提高 `23.3284 pp`。
四个模式均为 `1261/1261` 请求成功、`0` 错误；所有 `server_info_after.json` 中的
borrowed 计数均非负，且回收原因全部为 `global_overage`。

这组结果是当前设计的正式基线：固定保障份额提供 Agent 保护，borrow 只使用真实闲置
容量，需求回归时只归还 borrowed 页，不依赖工具时间、turn 时间或比例控制器。后续
压力和比例扫描应以该无水位配置为基准。机器可读结果和完整日志位于
`experiments/动态分区试验/results/validation_20261001_current_nowatermark/`。

## 当前 replay 的离线机制筛选

使用本次复核生成的 fixed `replay.jsonl`，在相同 page size、Full/SWA 容量和 61/39
保障份额下运行 page-level 离线模拟。该模拟不包含请求锁、并发 admission 和真实
生成，因此只用于筛选机制，不能替代 GPU serving。

| workload | 策略 | 总体命中率 | Agent 命中率 | 普通请求命中率 |
|---|---|---:|---:|---:|
| mixed_scaled | fixed_region_lru | 68.9168% | 74.1711% | 3.5672% |
| mixed_scaled | global_efficiency | 87.2371% | 94.2291% | 0.2744% |
| mixed_scaled | borrow_lru | 68.9168% | 74.1711% | 3.5672% |
| request → Agent → request | fixed_region_lru | 49.2255% | 51.9730% | 15.0529% |
| request → Agent → request | global_efficiency | 3.5357% | 0.0000% | 47.5108% |
| request → Agent → request | borrow_lru | 49.4501% | 51.9730% | 18.0713% |

global-efficiency 在两个 workload 上把收益完全推向不同区域，说明“按近期命中效率
统一排序”仍然依赖 workload；borrow_lru 保持 Agent 保障，并在阶段切换中释放少量
闲置容量。离线结果位于
`experiments/动态分区试验/results/offline_current_20261001/`，其限制条件已写入
每个 `results.json`。
