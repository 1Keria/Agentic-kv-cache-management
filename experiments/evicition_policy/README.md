## 1. 目标与边界

先回答三个问题，再考虑设计新策略：

1. Agent 会话的请求间隔、上下文增长、前缀复用和缓存竞争有什么规律？
2. 原生淘汰策略分别在什么情况下失效，造成多少可观测的重算和延迟损失？
3. 建立怎样一套可复现的工作负载与基线，供后续新策略公平比较？

本阶段的约束已经确定：

- **只使用来源明确的 Agent 执行轨迹**，首选 SkillsBench 中的 OpenHands 轨迹。GLM 线上流量与 WildChat 不进入本轮。
- **不训练、不加载身份分类器或复用预测小模型，不使用固定分区或动态分区，不使用自研淘汰策略。**
- 大模型推理服务仍然需要模型权重；默认继续使用 DeepSeek-V4-Flash，不将“不使用小模型”误解为不运行推理服务。
- 使用隔离的官方 SGLang 源码和环境；不把当前项目修改版仅关闭开关后称为“原生引擎”。
- 多个 Agent 会话竞争同一个逻辑缓存实例。Full/SWA 是模型自身的缓存池，不是 Agent/普通请求分区。

- 不预设某种策略获胜；无明显差异、仅局部改善或所有策略都受限，也是有效结论。

**现已实现** 数据准备、编码、画像、协议验证、回放与重启编排，以及自动验证和三策略执行链路。加速方案新增源等待/有效等待双记录、均匀时间缩放、长回放禁用旧 HTTP keep-alive 复用、完整性审计和缓存压力门禁；91 项单元测试通过。旧 25 会话验证只适用于旧 90 秒方案，新方案必须重新验证后才能放行。完整事件诊断未实现，不能据此给出精确淘汰归因。

4. 逐文件核验非空 JSONL、请求结构、可追溯的 Agent 配置、轮次、时间戳、响应与 usage；识别 LFS 指针、截断文件和重复文件。
5. 产出 `results/audit/data_inventory.json` 与 `data_audit.md`：列出清单数、实际文件数、去重数、任务数、请求数、缺失/异常数量以及各阶段排除原因。

来源不明确的数据不进入主集合；不使用 `n_system_messages` 或工具字段是否存在来决定请求身份。类别只由来源审计保证，也不发送给服务参与决策。

### 4.2 去重、完整性与划分

- 文件内容哈希去除完全重复副本；另用规范化请求序列指纹检查跨下载包重复。相同任务的不同有效尝试不直接合并为一个会话。
- 一个 Agent run 是一个会话。若原始日志存在分支或并行调用，记录依赖关系；无法恢复依赖的轨迹保留在画像里，但不强行串成主回放会话。
- 使用稳定的任务标识分组，避免同一任务不同 trial、配置或近重复轨迹跨越校准集和评估集。划分建议为任务级 20% 校准、80% 评估，种子 42，冻结清单。
- 这里的校准用于容量、回放和策略参数，不训练任何模型。评估集可以用于事后画像与归因，但不得反过来调参再报告同一轮成绩。
- 保留追加、历史改写、压缩、重试和已观测到的失败任务；不按“前缀长得好”或任务成功与否筛掉不利样本。
- 输入超过目标模型上下文上限、非文本格式不受支持或关键消息损坏时，保留在数据审计与可做的画像中；从主服务集合显式排除整个受影响会话，不悄悄裁剪 prompt。
- 缺失输出长度不自动设成 1；缺失时间戳不自动设成 0 秒。记录未知值及其影响。只完成了一段的会话标记为观察不完整。

最初以全部 **83 个完整评估会话 / 4,154 次请求**为覆盖目标；GPU 实测表明其输入和输出 token 量至少需要约 2 小时，不能只靠压缩等待满足一小时预算。当前快速探索改为从 83 个候选中按预注册 SHA256 顺序取 20 个完整会话；不复制会话、不截请求或输出，也不使用策略结果挑样本。结论范围仅限该冻结样本。

### 4.3 保留真实间隔，不制造“自然流量”

单条依赖边的间隔定义为：

```text
下一轮原始请求时间 - 上一轮原始响应完成时间
```

响应完成时间缺失时，只有确认 `duration_ms` 的含义、单位和起点后，才允许由请求时间加耗时推导，并标记为推导值。负值需要区分时钟异常与真实并行，不直接取 0。

- 该间隔首先叫“工具/编排等待”，没有工具起止事件时不称为纯工具执行时间。
- 主回放保留可靠的会话内部间隔，不沿用 30 秒上限，不统一压缩长等待。
- 独立任务的原始绝对时间不一定来自同一线上服务，不能拼起来称为真实跨会话到达过程。本轮显式构造跨会话启动计划，并将其标注为合成调度。
- 时间不可靠的轨迹仍可分析内容与前缀结构；如果另做合成等待实验，独立命名并单独报告。

## 5. 请求画像与待验证假设

### 5.1 基础画像

画像尽量覆盖全部可用原始 Agent 轨迹；正式服务回放只用冻结子集。所有 token 统计使用目标模型的实际 tokenizer、chat template、工具与推理内容处理方式，不用字符长度估算替代。

| 画像项目 | 统计口径 | 待回答的问题 |
|---|---|---|
| 会话形态 | 每会话轮数、观测时长、原始任务/模型、完成状态 | 长会话是否主导请求或 token 总量？ |
| 返回规律 | 完成到下轮到达的等待分位数、长等待比例；同时看期间其他请求引入的不同前缀块 | 被挤出是因为等得久，还是期间竞争大？ |
| 内容增长 | 输入/输出/工具返回长度、相邻轮新增长度；已有链的历史续接次数、新尾部出生与首次再需求 | 已经反复续接的链，其新尾部是否仍表现为冷内容？ |
| 复用结构 | token 级最长公共前缀、同会话/跨会话共享；公共祖先、私有历史、分支；追加、编辑、压缩 | 收益来自公共前缀还是会话续接？两者是否被混为一谈？ |
| 缓存需求 | 去重前缀块、复用间隔、服务中实际 Full/SWA 占用、锁定与可回收量（若可观测） | 多个会话的有效工作集如何竞争？ |
| 结束后占用 | 明确结束或在观察窗内未返回的前缀驻留；共享前缀单独计 | 有多少空间暂未产生后续收益？ |

最低产物：会话规模表、等待间隔分布、每轮增长与共享前缀分布、各形态占比。用完整前缀上下文标识块，不按相同 token 内容片段去重。逻辑 token 工作集不直接等于 V4-Flash 的物理 KV 字节数，Full/SWA 也不直接相加为“总可缓存上下文”。

等待期间分别统计“其他请求访问过的不同前缀块”和“其他请求新插入的不同前缀块”，不把访问热度当成新分配量。可验证物理映射时按池报告实际字节，否则只给去重逻辑 token/页和覆盖率；共享块不能在多个会话名下重复计入总占用。

### 5.2 区分在线可见信息与事后标签

| 信息 | 可见范围及用途 |
|---|---|
| 已提交输入、已经发生的访问、实际完成输出 | 服务当时已知；离线解析用于画像，不能注入服务改变本轮决策 |
| 会话 ID、工具调用名称、分支依赖 | 依接口/日志而定；客户端能关联不代表原生淘汰器已经能读到，报告实际可见位置 |
| 已完成的历史续接次数 | 在当前请求之前、同一可确认上下文链上发生的续接次数；不是轮次编号，也不是 radix 节点 `hit_count` |
| 明确结束、取消 | 只有协议或日志真有事件才记录；文件最后一行、一次生成结束均不自动代表 Agent 任务结束 |
| 下一次真实返回、未来不再使用、最终任务成败 | 仅用于事后解释；不得当作当时已知的淘汰依据 |

初次请求、已续接、分支、改写、明确结束/取消、观察中断分别标记。历史改写后重新确认链关系，不把原链的续接次数无条件赋给新分支；未知关系保留未知值。后续研究即使使用这些特征，也需另行证明线上提取途径，本轮不增加策略输入。

### 5.3 待验证的失效模式

下面是研究假设，不是已证实的结果：

| 策略 | 假设 | 希望观察到的证据 |
|---|---|---|
| LRU | 工具等待期间暂时不活跃的会话被过早淘汰 | 已移除的前缀随后很快再次需要，伴随未缓存输入和延迟增加 |
| LFU | 历史高频前缀失去价值后仍占空间，新会话受压 | 旧前缀持续驻留，而新会话在首次/早期返回时反复丢失缓存 |
| SLRU | 已反复续接的链不断产生新尾部，尾部自己的命中历史不足；旧保护前缀可能转冷 | 分开检查新尾部、节点分裂继承和保护状态，验证是否真的存在“链已热、尾部仍冷”的高损失群体 |
| TLRU | 固定新增长度估计不能覆盖长工具输出，或 token 预算不对应当前排队/计算代价 | 尾部淘汰后的下一轮未缓存输入超出预算，首 token 延迟恶化 |
| 多种策略共有 | 大上下文、共享祖先、回收粒度或活跃锁定占用主导损失，而非排序本身 | 多种排序差异很小，损失集中于相同结构或容量约束；仅提出后续准入/粒度研究方向，本轮不实现 |

仅凭“淘汰后又访问”不能证明该次淘汰可避免；必须区分容量不得不回收、候选受限与策略排序失误。

“续接资格迁移”仅列为可能的后续机制，不作为本轮对照，也不根据几个有利案例判定有效。若要证明另一种淘汰选择更好，必须满足相同释放空间与合法性约束，并计算被替代淘汰内容的后续损失，见第 9.5 节。

### 6.2 生效验证与降级路线

策略预检不只检查 `--help`，需包含：

- 启动日志/服务信息能确认真实缓存后端；模块路径来自隔离官方源码。
- 在小型确定性候选场景中核对评分排序，再在完整缓存组件中核对受锁和父子关系约束后的淘汰结果。
- 对 Full、SWA 两条实际回收路径分别确认是否使用所选策略；某条路径固定 LRU 时必须披露，不能称为全缓存池的同策略比较。
- GPU 小样本验证缓存确实发生回收，并观察到与预期一致的保留/命中差异；无需让所有策略在每个场景都产生不同结果。
- 至少覆盖：长间隔返回、重复热点与新前缀竞争、SLRU 门槛两侧、TLRU 可回收尾部不足/充足、共享前缀和锁定请求。

**基础对照优先完成 LRU、LFU、SLRU；TLRU 是同后端上的第四个候选。** 在正式计时前确定它能否加入；不为等待 TLRU 阻塞数据画像和基础三策略验证。若做不到：

1. 先完成画像，以及已经验证兼容的原生策略子集；未支持项明确写“未运行”，不得用 LRU fallback 冒充。
2. 记录阻塞原因、支持矩阵和官方版本证据；不移植或重写策略来凑齐原生对照。
3. 如果必须更换服务模型或改变实验主后端且会影响目标，先与用户确认；新后端上的所有策略重跑，旧成绩不直接混合。

### 6.3 首轮策略参数

| 策略 | 首轮参数原则 |
|---|---|
| LRU | 官方默认，无额外调参 |
| LFU | 官方默认，无额外调参 |
| SLRU | 显式记录官方 `protected_threshold=2`；暂不扫描门槛 [U1][U2] |
| TLRU | 在校准集估计 `next_prompt_estimate`，冻结一个有效 `threshold`；禁止看评估收益后挑最好参数 [U1][U2] |

TLRU 的可执行校准办法：

- 根据固定提交的具体长度语义，在校准集中确定“下一轮新增 token”的统计规则。对完整追加轨迹区分上一轮输入、实际/记录输出与新工具内容；历史改写另标，不把负增长当成新增长度。
- 用可解释的校准均值确定 `next_prompt_estimate`，记录使用了哪些样本及局限。
- 在无排队或低排队的小规模 prefill 测量中，取得未缓存 token 与耗时的关系。首轮用校准集追加请求新增长度的第 90 百分位确定一个初始 token 预算，并要求至少比估计均值多一个合法页面；两者取较大并向上按页对齐。
- 将该预算对应的实测首 token 延迟区间报告出来；它不是业务承诺。未来若用户指定延迟目标，再独立做预算敏感性实验。
- `threshold=4096, next_prompt_estimate=512` 只可作为接口示例，不直接当作本数据的最优参数。官方要求有效阈值大于新增长度估计 [U1]。

Priority、MRU/FIFO 等不进入第一轮主矩阵；也不把本项目 `agentic`、`reuse_value`、`mlp` 当原生对照。

### 6.4 记录实现语义，不能只写算法名

本次核对的官方评分器中，LRU 使用最后访问时间，LFU 使用命中次数再以时间打破平局；SLRU 用 `hit_count` 门槛划组、组内按时间排序。该 SLRU 评分实现没有独立的保护段容量配额，不能把其他文献里双队列定额、晋升降级的规则套到它身上 [U2]。

锁定版本后生成 `results/audit/policy_semantics.json`，记录计数初始化/更新时机、chunked prefill 是否更新计数、节点分裂如何继承计数、哪些池实际使用评分器、候选合法性和 TLRU 长度单位。固定版本必须实读树源码确认节点分裂是否继承命中计数；在确认前，“新节点都没有历史”不能当作前提 [U6][U7]。这些是核对与测试要求，不是给引擎增加规则。

## 7. 回放语义与历史回答不一致问题

### 7.1 主实验采用固定内容、会话依赖回放

- 优先使用官方原生 `/generate` 的 token 输入接口，冻结实际输入 token IDs，避免不同轮/策略的模板处理发生漂移；接口字段以锁定版本预检为准 [U3][U5]。
- 小样本核对模板、工具内容、特殊 token、输入长度及缓存前缀边界。若目标模板暂不能正确复现，停止构建正式负载，不静默删除字段。
- 每个会话首轮按冻结的启动计划发送，下一轮在前轮完成后等待原始间隔再提交。没有可靠依赖的并行轨迹不强行顺序化。
- 每轮输出长度使用经过核验的目标 tokenizer 口径；首选源记录中相同模型的 usage。固定生成长度、随机种子、采样与停止规则，并核验实际输出 token 数，不只检查 `max_tokens`。
- 不全局统一截成很短的输出。若数据中的完整输出使运行超时，应在校准阶段调整会话数量和启动密度，而不是事后截断某种策略。
- 请求和会话标识在客户端关联日志；不使用会话专属 cache salt 或新加提示词隔离前缀，以免人为消除跨会话共享。

这里冻结的是内容、启动计划、依赖和等待规则。由于前轮完成时间受服务性能影响，后续请求的实际到达时间允许变化；逐轮记录变化，不承诺各策略绝对时间和批次完全相同。

### 7.2 不把生成偏差误判为淘汰失效

记录中的下一轮历史回答可能不同于本次生成，即使 `temperature=0` 也不能预设与原轨迹相同。因此主实验是**历史请求回放**，不是工具驱动的在线 Agent 执行。

具体处理：

1. 保存每轮实际输入和生成 token IDs；计算下一轮输入与“本轮输入 + 本次真实输出”的最长公共前缀，并与原始轨迹相应前缀比较。
2. 用数个完整会话做低压力回放，确定模板、页边界、最后一个 token 重算等基线现象；不把它们归因于容量淘汰。
3. 将历史改写、首次出现、生成不一致导致的不可复用与事件证实的缓存移除分开。不能把 `prompt_tokens - cached_tokens` 全部称为“错误淘汰重算”。
4. 若不同策略实际输出内容不同且显著改变下一轮可复用历史，保留总性能结果，但增加生成一致/不一致分层；该子集不能支持“只由淘汰排序导致”的强因果结论。
5. 如果这种偏差主导结果，先停止策略归因，交付偏差报告；需要精确历史输出回放或真实 Agent 执行时另立阶段，不在原生引擎里临时插入自定义解码逻辑。

第一轮不开发复杂的 teacher-forcing 引擎，不宣称固定输出长度就保证固定输出内容。

### 7.3 离线分析的用途

固定事件时间的离线前缀分析用于画像、构造案例和解释竞争，不用来替代真实服务延迟。若以后补充理想化未来需求对照，明确它忽略哪些锁、树结构、压缩和双池约束，不把简单缓存模拟器称为 V4-Flash 的严格最优上界。

本阶段不强制开发完整多策略缓存模拟器。先对每次已采集的运行按事件顺序分析，只有插入、分裂、锁、回收、完成等事件足以恢复状态时，才开展确定性候选重放；仅有请求文本不能恢复真实合法候选集合。会话依赖回放使用记录的工具等待，不称为实际执行工具的 Agent 闭环，两者的性能结论分开。

## 8. 资源、压力选择与实验规模

### 8.1 初始服务配置只是预跑起点

沿用既有成功启动经验，预跑先尝试下列配置；正式值必须通过官方环境验证后写入锁定配置。

| 项目 | 预跑起点/要求 |
|---|---|
| 大模型 | 已有 DeepSeek-V4-Flash 权重目录 |
| GPU | 目标 8 张可用 H100、TP=8、单服务实例；运行前重新检查，不假定 GPU 当前空闲 |
| KV dtype | `fp8_e4m3`，前提是锁定官方版本支持 |
| 内存静态比例 | 0.45 起步，仅用于估算可用容量 |
| 页面、chunked prefill | 256、8192 起步，服从目标模型合法配置 |
| 最大运行请求数 | 256 为上限起点；校准时确认不会由排队/锁定占用掩盖缓存竞争 |
| CUDA Graph | 优先启用 decode；prefill 是否开启由该模型与官方后端兼容性实测决定，所有策略一致 |
| 其他 | 同一 attention backend、调度规则、并行方式和日志级别；随机种子 42 |

不为了填满卡而在同一组 GPU 上并行启动不同策略。GPU 服务串行，数据审计和结果分析可以在不影响服务的 CPU 资源上执行。

### 8.2 先选一个有代表性的中等压力点

本轮的预算是整个纯 Agent 服务实例的可用 KV 容量，不是给某一业务区域设置比例。移除普通请求后不盲目放大到无竞争容量，也不机械沿用旧分区的 61%；若以后需要衔接旧实验，可以额外复测相同绝对容量点，但不混入本轮主结论。

只在校准集上用 LRU 选择容量与会话启动密度：

1. 先以低竞争设置测量完整会话时间、排队和复用潜力。
2. 固定启动密度，逐步减少 KV 容量，使运行期间多次发生容量淘汰，同时没有 OOM、持续排队失控或大量请求撤回重算。
3. 若服务几乎没有缓存竞争，才增加跨会话重叠；若主要瓶颈是计算排队，降低启动密度，重新冻结校准配置。
4. 记录每档实际 Full/SWA 容量、占用、淘汰和排队指标，选中间档，而不是选择“某个候选策略收益最大”的档。
5. 正式策略间核对两类缓存池的实际页数/容量；不能只比较相同 `mem_fraction_static`。若后台内存变化导致容量不同，先修复控制变量再跑。

若后续扩展容量曲线，固定同一工作负载和启动计划，只改变容量。优先用锁定官方版本支持的容量上限控制；无法精确独立控制双池时，记录耦合关系，不虚构独立容量。

校准阶段先用同一个 5–10 会话子集完成轻/中/重三档容量覆盖，再冻结正式中间档。轻档主要检查复用语义，中档有持续可回收竞争，重档增加淘汰但不得 OOM 或排队失控；不是按任意三个内存比例命名。记录每池总预算、实际占用、活跃锁定、可回收和空闲量（以原生可见项为准），无法获取的字段明确缺失。引擎里表示锁定的 `protected_size` 与 SLRU 的“保护组”不是同一概念，不可互相代替 [U6]。

### 8.3 分阶段矩阵与运行预算

| 阶段 | 内容 | 数量与放行条件 |
|---|---|---|
| 数据/环境准备 | 全量画像、官方隔离环境、CPU 正确性测试 | 不运行正式 GPU 对照；数据与版本证据齐全 |
| GPU 预跑 | 少量完整校准会话、接口/兼容性与长度验证 | 小规模按需运行；不计正式成绩 |
| 小规模容量校准 | 同一个 8 会话校准子集，只用 LRU，从较大容量开始 | 先跑一档完整负载，再按观测决定是否继续减小容量；不运行候选收益搜索 |
| 第一轮探索性对照 | 同一份 20 个完整会话 / 1,206 请求的一小时评估 workload、一个冻结压力点 | 已完成 LRU/LFU/SLRU 各 1 次，共 3 次；TLRU 不在当前矩阵 |
| 失效诊断 | 对典型会话/竞争场景启用官方事件采集 | 最多先做每策略 1 次定向诊断；单独标记，不混入轻量计时结果 |
| 后续扩展，非第一轮硬要求 | 轻/重压力各比较 LRU 与一个已冻结选择的候选 | 每档每策略 3 次，共 12 次；选择依据公开，不宣称独立验证了新的最优策略 |

本轮三种策略使用同一份完整工作负载，内容、首轮时间表、会话依赖、等待及输出长度规则一致；实际后续到达时刻仍受本地生成耗时影响。先用 LRU 的校准结果确定容量点，再看其他策略表现，不得为了最大化策略差距重选容量。已有 393 请求 LRU 校准不算这 3 次中的一次。小规模校准数据与评估数据分开，不能混成同一条容量曲线。

本轮只运行以下一行；每个策略都独立启动、同样预热、清缓存、完整回放、停止并确认释放：

| 当前阶段 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 探索性单轮 | LRU | LFU | SLRU |

单轮不是顺序平衡设计，无法分离运行顺序影响，也无法估计每个策略的运行间波动。当前只报告本轮观测差异与诊断线索，不声称稳定领先或统计显著。下一步建议缩小为 LRU/SLRU 两策略，至少分别执行 `LRU → SLRU` 与 `SLRU → LRU` 的顺序平衡重复；LFU 暂不优先。新批次必须保持配置、数据和预热不变，不能与失败或部分运行拼接。

旧方案不压缩等待，完整 83 会话单次约需数小时；0.25 倍全量方案又因平均排队 12.259 秒被门禁否决。最终一小时方案按固定哈希顺序选择 20 个完整会话，不截其中任何请求或输出；跨会话启动和会话内等待统一乘 0.30，KV 容量同步缩小 20%。正式集实测前预算为测量约 40–45 分钟，加启动、预热和释放约 55–60 分钟。实际耗时仍由生成吞吐和排队决定；2 小时安全超时只会令运行失败，不会产生“完成”成绩。

### 8.4 每次运行的固定生命周期

1. 校验输入哈希、配置、官方模块路径、磁盘空间、GPU/端口占用，创建唯一 `run_id` 和 `running` 状态。
2. 启动独立服务进程组，保存完整启动命令、服务日志和模型/服务器信息。
3. 用固定校准子集预热合法形状和图编译；所有策略使用同一预热流程。
4. 等待在途请求结束，调用官方缓存清空接口，检查成功；以此划分预热与测量窗口，并使用测量窗口的指标增量 [U3]。
5. 回放冻结评估负载；逐请求落盘，周期性刷新运行状态和采样指标。
6. 等待全部会话完成，保存最终服务信息、汇总和完整性检查结果，再写 `completed`。
7. 停止本次服务进程组，确认自身 GPU 子进程和端口退出，再启动下一策略。禁止用全局 `pkill` 清理他人任务。

超时、中断或错误保留全部日志与状态。只有完整性合格的运行进入对照；中断重跑须新建记录，不覆盖失败证据，不在暖缓存上续跑后一半。公平检查失败时整次运行标记无效，不通过挑出成功请求来“修正”成绩。

## 9. 观测与归因：优先使用原生能力

### 9.1 两种观测模式

**正式计时模式：** 客户端请求日志、原生 usage/cache 字段、低频服务指标和 GPU 采样，所有策略采样设置一致。

**诊断模式：** 额外订阅官方 KV 事件。上游定义了存储、移除、清空等事件和序列/回放机制 [U4]；锁定版本、实际后端是否完整发布仍需预检。不假设存在每次访问、全部候选评分、锁状态或每类池的详细事件。

- 先在已知存储/回收场景检查事件覆盖、顺序、丢失和复用关联；按独立缓存实例统计，不把 TP 各 rank 的副本累计八次。
- 使用前缀链标识、token 位置和实际输入关联后续需求；单纯看到相同文本不代表复用了同一块 KV。
- 订阅就绪后再进入诊断窗口；保存事件序号，能重取的缺口尝试重取，无法补齐的窗口不做确定性归因。
- 原生事件无法区分 Full/SWA 或只覆盖逻辑前缀时，报告明确限定范围，不推出两个物理池的完整驻留图。
- 对比开启/关闭事件采集的预跑开销；正式轻量计时与详细诊断分开，不能把采集开销当策略代价。
- 第一轮不修改引擎加入观测补丁。确实缺少关键证据时，报告缺口；需要补丁则另行确认，不能悄悄污染原生基线。

### 9.2 历史前缀参照与额外重算

为区分“本来就是新内容”和“已经出现过但被容量淘汰”，增加一个只保存元数据的历史前缀参照索引。它不参与服务决策，也不保存生成文本副本；使用与目标模型相同的 token、chat template、缓存命名空间和页对齐规则，记录前缀身份、出现/再需求时间、逻辑长度、分支关系、观察完整性和来源运行。

每个请求到达时，先计算两种匹配长度：

```text
h_history  = 只要历史事件中仍能证明存在过，就能匹配的逻辑前缀 token 数
h_policy   = 当前服务实际报告的有效缓存命中 token 数
extra_recompute = max(0, h_history - h_policy)
```

`h_history` 不是无限容量下 V4-Flash 的严格物理命中上界：只有当历史索引能复原相同的插入、split/merge、锁和页匹配语义时，才能升级为事件忠实的参照。第一版先把它称为**历史可复用参照**，并同时输出以下分解：

- 首次出现或历史改写：历史参照本身不存在；
- 生成内容不一致：上一轮输出与下一轮记录历史无法拼接；
- 已知移除后再次需要：有事件证据支持容量或清空造成的损失；
- 参照与物理命中不一致但原因未知：不强行归因；
- 观察窗口不足：后续需求可能尚未出现。

只有在事件顺序能够覆盖存储、访问、split/merge、锁定、回收和清空边界时，才将 `extra_recompute` 的子集报告为“淘汰导致的额外处理 token”。在没有这些事件时，它只是诊断量，不能直接称为策略错误，也不能把 `prompt_tokens - cached_tokens` 全部计入。

参照索引必须使用**同一份请求流**，并按同一 token 前缀和缓存命名空间关联；不以相同文本片段跨上下文拼接，不把会话 ID 代替物理前缀身份。共享祖先只计一次逻辑容量，按会话展示时可标注引用关系。

### 9.3 最低可用记录

每个请求记录 `run_id`、策略、任务/会话/轮次、输入指纹、输入长度、期望/实际输出长度、预定首轮到达、实际提交/首 token/完成时间、原始等待、实际等待、缓存字段、状态和错误。实际输入/输出 token 序列保存在可关联的受控文件中。

首 token 时间只计真实生成 token，不把空文本、角色块或 usage 消息当首 token。usage 中缺少 cache 字段时标为未知，不默认置零。原生排队/prefill/decode 时间只在字段确实存在且含义核对后报告。

每次运行至少保存：

```text
config.resolved.json       manifest.json              environment.json
command.txt               server.log                 replay.jsonl
server_info_before.json   server_info_after.json     metrics.jsonl
gpu_samples.jsonl         integrity.json             summary.json
run_status.json           outputs/                   kv_events/（诊断模式）
```

环境信息使用白名单，不直接转储全部环境变量、令牌、访问凭据或完整敏感 prompt 到公开报告。终止和分析工具同样只操作本实验记录的路径/PID。

### 9.4 指标定义

| 指标 | 定义和限制 |
|---|---|
| token 加权命中率 | 原生有效命中 token 合计 / prompt token 合计；先验证字段语义 |
| 未缓存输入量 | prompt token 减命中 token；是代理指标，不等于全部是多余重算，也不等于 GPU 实际计算量 |
| 事件证实的复用损失 | 之前确实存在、随后移除、以后输入再次需要的相同前缀；剔除清空边界与不完整事件窗口 |
| 短期再次需求比例 | 移除后 5/20/60 秒内再次需要的 token / 具有完整相应观察窗口的移除 token；按池/事件可见范围报告 |
| 暂未复用驻留 | 在完整观察窗口内未再使用的可识别前缀驻留量与时长；不命名为“永不复用”，共享块不重复归属 |
| 延迟 | 请求首 token p50/p95/p99、请求完成时间、会话完成时间；会话时间包含固定工具/编排等待，并单列服务耗时 |
| 超标率 | 对事先在校准阶段冻结的延迟参考线统计；无业务目标时标为实验参考，不包装成业务 SLO |
| 策略开销 | 仅报告原生可观测的回收/调度耗时；缺少专用计时则写不可测，不以 TTFT 差值代替 |

短期再次需求按“前缀被请求需要”计算，不要求发生实际 cache hit。缓存节点 split/merge 后需要维持前缀身份；不能直接用暂时性的 node ID 贯穿全程。事件批次时间不等于精确淘汰时刻时，给出时间精度限制，对阈值边界样本保守处理。

### 9.5 归因等级

- **可直接确认：** 新内容首次出现、输入前缀改变、事件中明确移除后再次需要。
- **有证据支持的解释：** 长等待期间出现大量竞争；高频旧前缀仍驻留而新前缀丢失；需给出具体时间线和数据。
- **尚不能确认：** 当时一定存在更好的合法候选、某池锁造成了某次选择、某块永远不会再访问。无候选/锁或完整未来证据时不得升级结论。

首次访问、历史改写、生成偏差、容量淘汰和引擎约束可能交叠。报告使用明确标签与未知桶，不强行构造一个看似精确、实际上不可辨识的百分比分解。

### 9.6 三类首轮诊断产物

第一轮不要求复杂可视化平台；用分析脚本生成可复查的表格和三张基础图即可：

1. **容量—额外处理曲线**：横轴为校准阶段冻结的实际 Full/SWA 容量，纵轴为历史参照与当前命中之间的额外处理 token，以及事件证实的淘汰损失。只连接相同工作负载和相同调度计划的点；轻/中/重三档用于探索，不能直接当成策略最优曲线。
2. **损失分桶图**：按历史续接次数、等待时间、等待期间其他请求新插入的逻辑页量、新增上下文长度、共享/私有结构和失效原因分桶，同时给出样本数、token 数和观察完整性。不要只画命中率。
3. **驱逐时间线案例**：展示某次请求前的候选合法性、策略排序、释放页/token、后续再次需要时间、实际命中和参照缺口；如没有足够候选或事件证据，就把案例标为“无法确认策略可避免”。

这三类产物必须同时保存原始明细表和生成配置。图中缺少事件、未知时间或生成偏差的样本单独着色或排除并说明，不用插值填充。

## 10. 分析与验收标准

### 10.1 对照分析

- 主指标预先指定为 token 加权命中率、未缓存输入量、首 token p95/p99；同时报告会话完成时间与诊断证据，不用单项最优决定胜者。
- 每种策略分别生成单次指标，与本轮 LRU 比较绝对变化和相对变化；这不是三组重复结果。命中率的“百分点”和“百分比”分开，公开原始数值，不只给相对收益。
- 每种策略只有一次运行，运行间波动和顺序影响无法估计，不宣称统计显著或稳定领先。任务/会话分组用于展示异质性，不把其中的每轮请求当作独立实验重复，也不以请求数量代替重复次数。
- 按会话长度、等待区间、历史改写、工具返回长度等预定义分组，展示样本数与效果。请求加权、token 加权、会话等权结果不要混用。
- 稀有形态与尾部样本不足时附样本数/原始尾部列表，不仅给出 p99。跨会话共享不足以代表其他 Agent 框架时明确范围。
- 固定到达计划下的完成吞吐不是饱和吞吐上限；更短的闭环完成时间也不等于任务质量改善。

### 10.2 分阶段交付与完成条件

| 交付 | 必须达到的条件 |
|---|---|
| 数据审计 | 所有入选会话可追溯到 Agent 来源；去重、划分、时间质量、过滤和哈希可检查 |
| 请求画像 | 核心五类规律有统计与样本量；真实间隔和合成调度分开，观察不完整样本未误标为永不返回 |
| 原生支持矩阵 | 官方提交/模块路径/实际后端已固定；每个被报告策略确实在目标回收路径生效 |
| 可重放基线 | 脚本、依赖、启动参数、输入/输出规则、容量与图设置完整；从独立重启可复现 |
| 有效对照运行 | 工作负载与输入逐请求一致；请求数及实际输出长度符合冻结规则；无错误/漏请求；实际容量相同；状态完整 |
| 失效案例 | 每个有证据的模式给出请求和前缀时间线；没观察到也如实记录，不为每个策略硬编一个案例 |
| 最终报告 | 区分观测事实、归因解释、待验证假设；说明哪些模式值得后续研究、哪些没有足够收益空间 |

汇总前的硬失败条件：意外导入修改版引擎、分类/分区/自研策略介入、CLI 名称与实际策略不符、容量不一致、输入变更、输出长度不受控、漏请求/超时/错误。输出内容偏差与诊断事件缺失另设归因质量标记：可以保留合格的服务性能数据，但不能据此宣称完成精确淘汰归因。

## 11. 实施顺序与决策点

1. **恢复并审计原始数据**，确认 V4-Flash 来源的有效任务和时间质量。数据缺失时先解决来源，不能拿加工 workload 冒充。

5. **已完成第一轮单次探索性对照**；下一阶段对 LRU/SLRU 执行顺序平衡重复，每次重启并及时保存结果，不在中途根据成绩修改数据或参数。
