# LRU、LFU、SLRU 三种传统淘汰策略：实测与原因分析

日期：2026-10-07。本文基于正式 suite `results/runs/20260928T015431Z_a6d1c132/` 的三次完整运行，并重新生成了逐请求和闭环交错分析。每种策略只运行一次，因此结果用于筛选候选和提出机制假设，不用于统计显著性声明。

2026-10-08 更新：LRU/SLRU 已完成两批顺序互换复验，小幅优势没有稳定复现；最新结论见 [顺序互换复验报告](传统淘汰策略顺序互换复验_20261008.md)。本报告保留此前三策略单次运行的历史数字，LFU 本轮未复跑。

## 结论

在当前固定 Agent-only 压力点，**SLRU 是最值得继续复验的传统基线**：命中率最高，达到 66.5342%，相对 LRU 多命中 233,472 token（+0.4785 个百分点），TTFT p95 低 5.99%。但它的净收益很小，来自少数长链的正负翻转，不能直接作为最终 Agent 策略。

**LFU 不适合作为当前 Agent 区域的直接候选**：命中率比 LRU 低 1.9320 个百分点，少命中 942,592 token；原生回收计数高 48.27%，回收时间总和高 186.19%。这与“累计频率会保留旧热点、挤压近期长链”的机制解释一致。

LRU 仍应保留为主基线。下一阶段应先在固定输入和完整 KV 事件下复验 LRU/SLRU，再决定是否加入有界的链续接信号；不要把原生 LFU 直接移植到 Agent 区。

## 实验口径

| 项目 | 设置 |
|---|---|
| 引擎 | 官方 SGLang 0.5.13.post1 |
| 缓存后端 | UnifiedRadixCache |
| workload | 20 个完整 Agent session，1,206 请求 |
| 输入/输出 | 每策略 48,787,785 / 693,217 token |
| Full / SWA 容量 | 524,288 / 52,224 token |
| page size | 256 token |
| 回放 | 同一固定输入，间隔缩放 0.30 |
| 策略顺序 | LRU → LFU → SLRU |
| 重复次数 | 每策略 1 次 |

本引擎路径中策略选择只影响 Full component；SWA 驱动的回收仍走原生 LRU，并且可能耦合释放。因此这里是“纯 Agent 请求下的 Full 评分策略对照”，不是两个物理池都独立切换策略的实验。

策略实际语义如下：LRU 按最近访问时间；LFU 按累计命中次数再按时间；SLRU 在 `hit_count < 2` 的 probationary 与 `hit_count >= 2` 的 protected 之间分组，组内仍按时间排序，且没有独立保护段容量配额。

## 结果

| 策略 | 命中率 | 命中 token | TTFT p50 / p95 | 请求耗时 p50 / p95 | 回收 token 计数器 | 回收耗时总和 |
|---|---:|---:|---:|---:|---:|---:|
| LRU | 66.0556% | 32,227,072 | 0.590s / 14.840s | 7.472s / 42.995s | 158,650,368 | 437.489s |
| LFU | 64.1236% | 31,284,480 | 0.456s / 14.501s | 7.641s / 41.901s | 235,229,184 | 1252.033s |
| SLRU | **66.5342%** | **32,460,544** | **0.459s / 13.951s** | **7.070s / 41.694s** | 159,455,232 | 432.870s |

相对 LRU：

- SLRU：命中率 +0.4785 个百分点，+233,472 token；逐请求 117 个更好、107 个更差、982 个相同。正向差异 1,893,376 token，负向差异 1,659,904 token，净收益只保留正向差异的 12.33%。
- LFU：命中率 -1.9320 个百分点，-942,592 token；逐请求 107 个更好、157 个更差、942 个相同。正向差异 1,331,200 token，负向差异 2,273,792 token。
- 三种策略均完成全部请求，0 retraction、0 monitor error。LFU 的 TTFT/E2E p95 略低于 LRU 不能直接解释为命中更好：LFU 与 LRU 的提交排名在 1,091/1,206 请求上发生变化，说明闭环交错和运行噪声已经改变。

## 为什么 LFU 在这里较差

1. **Agent 访问是长链续接，不是稳定的全局热点集合。** 非首轮转换中 1,127/1,186（95.03%）是严格 append。一次链上的早期节点可能累计高频，但另一条链的近期长前缀会在下一轮立即需要；累计频率没有时间衰减，容易把容量给旧热点。
2. **差异集中在大额长前缀翻转。** 逐请求分析中有 114 个 `lfu_loss_only` 案例；例如 `drone-planning-control` turn 57 少命中 109,312 token，`fix-build-agentops` turn 109 少命中 88,320 token。它们的 prompt 都很长、前一轮 LCP 很长，表现为整段链被重新计算，而不是零碎 token 小差异。
3. **回收压力和实现开销也更高。** LFU 原生回收 token 计数器为 235,229,184，LRU 为 158,650,368；回收耗时总和为 1252.033s 对 437.489s。计数器混合 Full/SWA，不能当作单池精确淘汰成本，但方向与 LFU 命中损失一致。

这里的解释是和观测相符的机制假设，不是同一缓存状态下的反事实证明；要下因果结论，仍需完整 candidate/victim/lock/split 事件。

## 为什么 SLRU 有少量收益又会反转

SLRU 的二次命中门槛能把一部分近期再次访问的节点放进 protected 组，因此在少数长链窗口中延长了可用前缀。它在 `drone-planning-control` 一条会话上净多 305,664 token，在 `fix-erlang-ssh-cve` 上净多 82,688 token；最大单请求收益为 121,088 token。

但这种保护不是普遍改善：同一窗口也出现 SLRU 少命中 117,504 token、83,712 token 等大额反例；8 个会话同时出现 SLRU 赢和输的 cliff。最长连续高前缀保持运行是 SLRU 56 轮、LRU 44 轮，但两者 high-to-high 保持率分别约 93.53% 和 93.42%，整体差距很小。说明 SLRU 的净收益来自少数大额翻转，而不是所有热链都稳定受益。

另一个限制是当前实现的 `hit_count` 会混合插入、真实匹配和结构 split 继承；SLRU 没有经典实现中的独立 protected 段容量。因此“SLRU protected”不能直接解释为“该尾部已被下一轮真实访问证明”。

## 三种策略共同暴露的问题

- 356/1,206（29.52%）请求在三种策略下都有至少 8K 的相邻前缀缺口代理，只有 108 个请求对策略达到至少 8K 的命中差异。大量损失不由排序差异决定，可能来自容量边界、活跃请求占用、Full/SWA 耦合、radix 节点释放粒度或准入。
- 固定输入内容中跨 session 共享的完整前缀页只有 12 个；主要收益空间是同一 session 的私有长链，不应优先做语义或全局频率共享。
- 当前日志中的相邻 LCP 缺口是内容级 proxy；没有逐次合法候选集合和 victim 事件，不能把它当成确切“错误淘汰重算”。

## 对后续 Agent 策略的直接启示

1. LRU 作为基础排序保留。
2. 原生 LFU 暂不直接采用；如果要使用频率，必须加入时间衰减或窗口化，并验证它不会压住近期长链。
3. SLRU 作为传统强基线继续复验，但应把 protected 解释为候选优先级，而不是确定的未来复用证明。
4. 下一版优先实现或验证一个简单、可回退的链级机制：只给刚暴露的父节点或新增尾部有限、短期的续接保护；每次回收保持相同释放预算，资源不足时回退 LRU。
5. 先补 Full/SWA 分池事件，再在固定输入下比较 LRU、SLRU 与新机制；否则策略收益会被共同的 SWA/粒度问题掩盖。
