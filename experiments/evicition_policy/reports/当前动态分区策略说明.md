# 当前动态分区策略说明

更新时间：2026-10-05  
状态：当前候选实现，已完成短压力 workload 的有效复核，仍需在更长、更多流量比例的 workload 上验证泛化性。

## 1. 方法概览

当前方案不是为 Agent 区单独设计一套新的 LRU/LFU/SLRU 排序，而是在混合流量下增加一层动态分区控制：

> **小模型在线分类 + 两类请求最低保障 + 共享弹性池 + 借用尾部分段 + 基于真实重算反馈的保护。**

系统把请求分为 `agent` 和 `request` 两个区域。两类请求各自拥有最低保障，但没有永久固定的容量比例。某一侧可以使用另一侧暂时空闲的空间；出现压力时，优先释放可借用的部分。区域内部仍使用原有缓存淘汰策略，本轮实验使用 LRU。

这里的“共享弹性池”是**容量语义**，不是第三个缓存区域：缓存中仍然只有 `agent` 和 `request` 两种逻辑所有者，每个节点仍带有自己的 `cache_region`。共享的是两侧对未使用物理 KV 容量的使用权，而不是请求之间的前缀命名空间或 KV 数据。两类请求仍然通过区域标识隔离缓存匹配。

方法不读取工具调用时长、turn 返回时长，也不使用离线统计得到的 Agent/request 流量比例。它只使用请求到达后已经观察到的分类、缓存访问、驻留量、驱逐和实际重算事实。

## 2. 请求分类与缓存命名空间

请求在 tokenizer 进程中由一个小型 MLP 分类器处理一次，输出：

- `agent`
- `request`

当前分类器使用的在线特征包括：

- 是否包含 tools；
- tool 数量、schema 长度和 tool call 数量；
- 是否已经出现 tool call；
- 消息数量和内容长度；
- 最大生成长度。

分类结果会随请求传入调度器和缓存。缓存 key 的 `extra_key` 会加入区域标识：

```python
("__request_cache_region__", cache_region, extra_key)
```

因此 Agent 和普通请求即使 token 前缀相同，也不会因为分类不同而错误共享同一条缓存路径。分类器失败时当前实现默认归入 `request` 区域。带 session 的请求还会尽量保持 session 已确定的区域，避免同一条链路在两个区域之间来回漂移。

## 3. 最低保障与共享弹性池

当前候选配置为：

```text
policy = elastic
agent_ratio = 0.50
agent_min_ratio = 0.20
agent_max_ratio = 0.80
activity_window = 32
preferred_reclaim = true
soft_step = 0.10
```

当两类请求都在最近的在线活动窗口中出现时，缓存容量 `C` 的保护线为：

```text
Agent 最低保障：0.20 C
普通请求最低保障：0.20 C
共享弹性池：0.60 C
```

例如总容量为 100K token 时，原则上至少为两侧分别保留 20K，剩余 60K 可被当前更活跃的一侧使用。

实现上没有单独创建一个名为“共享池”的第三个 allocator。Full 和 SWA 各自拥有物理 KV pool，区域统计记录每一侧的驻留量和借用量；所谓共享池，就是总容量减去两侧最低保障后的可借用容量。

这两个 20% 是保护线，不是永久静态分配。若普通请求当前只驻留 5K，Agent 可以使用普通请求没有使用的空间；普通请求重新出现时，系统会先释放 Agent 的借用尾部，为普通请求恢复空间。

当最近 `32` 次在线缓存访问中只有一类请求出现，系统暂时使用配置中的中性比例 `0.50/0.50` 作为返回保障线。这样可以避免把暂时没有出现的类别误判为永远不再返回。这里的 50/50 是冷启动和回访保护线，不是由离线流量比例预测得到的。

例如在总容量 100K、最近 32 次访问全部是 Agent 的情况下，系统暂时把 Agent 和普通请求的基准线都记为 50K。Agent 可以继续借用普通请求当前没有使用的部分，但超过 50K 的 Agent 节点会标记为 `borrowed`；这不是把物理容量硬限制在 50/50，也不是创建第三个区域。普通请求一旦重新出现，两侧都变成近期活跃，基准线恢复为 Agent 20K、普通请求 20K，Agent 的借用尾部在压力下优先释放。

因此，`0.50` 是一个预先配置的中性回访保护常数，但不是根据历史 workload 比例估计出的比例。它避免了在没有证据时直接给活跃侧更大的“永久保护额度”。

因此，`agent_ratio=0.50` 在当前方案中主要承担两个作用：

1. 冷启动时的中性保障线；
2. 软边界的初始位置。

当前 `elastic_feedback=false`，所以运行中的比例控制器不会根据累计驱逐量不断修改这个基础比例。动态性主要来自共享池、驻留比例形成的软回收边界和借用节点回收，而不是一个持续追踪流量比例的控制器。

## 4. 借用节点与尾部分段

请求插入缓存时，系统会判断新内容是否跨过本区域的最低保障线：

- 保障线以内的节点保持普通 Radix 结构；
- 超过保障线的节点标记为 `borrowed`；
- 超过当前软边界的借用节点进一步标记为 `preferred_borrowed`。

两种标记不是并列的请求类别，而是两层回收资格：

| 标记 | 代表什么 | 回收优先级 |
|---|---|---|
| `borrowed` | 节点超过本区域的最低保障线，使用了共享容量 | 可以进入 borrowed 回收候选 |
| `preferred_borrowed` | `borrowed` 节点中又超过当前软边界的部分 | 在 borrowed 候选中优先回收 |

因此 `preferred_borrowed` 是 `borrowed` 的子集。这里的 `preferred` 指“优先作为回收对象”，不是“优先保护”。例如 Agent 最低保障是 20%，当前软边界是 60%，Agent 使用 75% 时，20% 到 75% 都属于 borrowed，其中超过 60% 的约 15% 会被标记为 preferred borrowed。压力出现时先处理这 15%，再处理其余 borrowed；只有 borrowed 空间不足时，普通区域 LRU 才会作为回退进入保障线以内的节点。

当前配置为：

```text
borrowed_segment_tokens = 1024
page_size = 256
```

传统 Radix Cache 可能把一个很长的新后缀存成一个完整叶子节点。若这个叶子被淘汰，可能一次性删除很大的上下文。当前实现只对跨过保障线的尾部进行切分，并按 page 对齐形成最多 1024 token 的借用段。保障线以内的公共前缀不被无条件切碎。

例如一个 Agent 请求已经占用到保障线，再新增 5K token 时，新增部分会被拆成若干个可独立回收的尾段。这样回收时可以先释放较新的尾部，保留已经被多次续接的较老历史。

## 5. 软回收边界

共享池中的 preferred 边界根据当前驻留 mix 在线计算：

```text
observed_agent_ratio =
    Agent 已驻留 token /
    两类已驻留 token 总量
```

这个比例被限制在 `20%` 到 `80%` 之间。当前 `soft_step=0.1`，因此软边界每次最多移动 10 个百分点，而不会因为一次请求突然从 50/50 跳到 80/20。

软边界只决定借用节点的优先级，不是一个强制的物理容量切割。例如普通请求没有达到自己的保障线时，Agent 可以暂时使用空闲部分；当普通请求产生压力，Agent 借用尾部会重新成为优先回收对象。

如果缓存物理上已经接近满载，而某一侧尚未达到自己的最低保障，系统会优先考虑活跃侧最新产生的借用尾部。这样可以尽量保留较老的共享前缀和 Agent 历史。

## 6. 压力下的回收顺序

当新请求需要空间时，`elastic` 模式首先计算当前区域在保护另一侧已驻留内容后能够使用的有效空间：

```text
当前区域有效上限 = 总容量 - 另一侧已驻留 token
```

如果新内容会超过这个上限，系统按下面的顺序回收：

1. 优先回收 `preferred_borrowed` 节点；
2. 当前实验默认先回收 `request` 区域的借用节点；
3. 普通请求借用空间不足时，再回收 Agent 区域的借用节点；
4. 借用节点不足时，才进入对应区域内部的普通 LRU 回收。

默认的 `request_first` 顺序用于尽量保护已经建立起来的 Agent 长链上下文。工程上还保留 `pressure_first` 选项，但它不是当前候选配置。

当前回收顺序不会直接把两个区域的所有节点混在一起重新排序。它先利用区域所有权和 borrowed 标记缩小候选集，再在候选集内部使用原有策略。

## 7. Ghost：基于真实重算的保护

Ghost 可以理解成“被淘汰 KV 的影子记录”，类似缓存替换算法中的 ghost list：KV 本身已经释放，但系统保留一个很小的元数据记录，用来判断这次淘汰后来是否真的造成了损失。

一个完整的时间线是：

```text
前缀 P 在缓存中
        ↓ 压力导致 P 被淘汰
Ghost 只留下 P 的指纹和长度，不留下 KV
        ↓ 后续请求再次需要 P
当前只命中 P 的一部分，缺失部分必须重新计算
        ↓
Ghost 给 P 增加“真实重算损失”分数
        ↓ P 重新插入缓存后再次遇到压力
Ghost 让 P 在 borrowed 回收中延后被淘汰
```

如果前缀被淘汰后从未再次访问，Ghost 不会凭空认为它有价值；如果再次访问时已经完整命中，也不会产生新的损失分数。只有“先被淘汰，之后又因为缺失而实际重算”的情况，才会触发保护。

节点被淘汰时，系统不会保存 KV tensor，只保存有限的元数据：

- 从根节点到被淘汰节点的完整 page 对齐前缀指纹；
- 所属区域；
- 前缀长度；
- 淘汰次数；
- 后续回访导致的重算 token 数；
- 按请求事件衰减后的 revisit score。

当前配置为：

```text
ghost_capacity_tokens = 1,048,576
ghost_pressure_decay = 0.995
ghost_protect = true
ghost_protect_min_tokens = 1,024
ghost_reclaim = false
ghost_bias = 0
```

后续请求到达时，Ghost 会将当前实际命中的前缀与历史指纹比较。例如：

```text
历史上曾缓存到：16K token
当前实际命中：10K token
因之前淘汰而产生的额外重算：6K token
```

这 6K token 会增加对应历史前缀的 revisit score。分数按请求事件衰减，而不是按墙钟时间衰减，因此不需要预测工具返回时间或下一轮 turn 到达时间。

当某个借用节点对应的历史前缀保护分数达到至少 1024 token 时，它在下一轮借用区域回收中会被延后处理。保护只改变借用候选的优先级：

- 不影响普通区域内部的 LRU；
- 不会把节点永久固定在缓存中；
- 如果所有合法候选都具有保护分数，系统仍然可以回收其中的节点；
- 不会改变当前跨区域的 `request_first` 顺序。

Radix 结构发生 split 时，节点旧的 Ghost 指纹和分数会清除并重新建立，避免结构变化后把旧保护错误地赋给新的后缀。

### 7.1 一个带参数的数值例子

下面用一个 100K token 的物理缓存说明一次完整过程。假设两类请求都在最近 `activity_window=32` 个访问事件内出现，因此两侧最低保障都是 20K：

```text
总容量 C = 100K
Agent 最低保障 = 0.20 × C = 20K
普通请求最低保障 = (1 - 0.80) × C = 20K
共享弹性容量 = 60K
```

假设当前驻留量为 Agent 70K、普通请求 30K。当前观察到的 Agent 驻留比例为 70%，但软边界之前是 50%，所以在 `soft_step=0.10` 下，本次只移动到 60%；如果下一次仍然观察到相近比例，才会继续移动到 70%。此时：

```text
Agent borrowed = 70K - 20K = 50K
Agent preferred_borrowed = max(70K - 60K, 0) = 10K
普通请求 borrowed = 30K - 20K = 10K
普通请求 preferred_borrowed = max(30K - 40K, 0) = 0
```

如果普通请求又需要 12K，而物理缓存已经满了，则普通请求的有效上限为 `C - Agent 已驻留量 = 30K`，需要先释放 12K 借用空间。当前 `request_first` 的回收顺序大致是：

1. 普通请求 preferred borrowed（这里为 0）；
2. 普通请求普通 borrowed（最多释放 10K）；
3. Agent preferred borrowed（再释放 2K）。

现在考虑 Agent 的一个 16K 前缀 P。P 之前被淘汰时，Ghost 只保存了 page 对齐指纹；后来请求再次需要 P，但实际只命中 10K，于是：

```text
本次真实重算 = max(16K - 10K, 0) = 6K
Ghost revisit_score(P) = 0 + 6K = 6,144 token
```

因为 `6,144 >= ghost_protect_min_tokens=1,024`，P 重新插入后会在 borrowed 回收候选中被延后。如果 Agent 的其他 preferred borrowed 段没有 Ghost 分数，系统会先回收那些段；只有没有未保护候选时，P 才可能被回收。Ghost 不会改变前面“普通请求先于 Agent”的区域顺序，因为当前 `ghost_reclaim=false`。

如果下一个请求事件没有新的回访损失，P 的分数会先衰减为：

```text
6,144 × 0.995 = 6,113.28 token
```

如果之后再次因为淘汰产生 2K 重算，分数大致变为：

```text
6,113.28 + 2,048 = 8,161.28 token
```

如果 P 被淘汰后从未回访，它不会获得分数；如果回访时已经完整命中，也不会增加分数。这说明 Ghost 保护的是已经被真实重算证明有价值的历史，而不是根据 session、等待时长或语义相似度提前预测价值。

## 8. Full 与 SWA 的一致性

Full 和 SWA 的工程回收路径不同：

- Full 使用 Full LRU 和 Full token pool；
- SWA 使用 SWA LRU，并处理 sliding-window tombstone；
- 两类物理容量、可回收量和驱逐统计分别维护。

但二者使用同一种分区策略：

- 相同的 `agent/request` 标签；
- 相同的最低保障线；
- 相同的共享弹性池；
- 相同的 borrowed 和 preferred borrowed 标记；
- 相同的 1024-token 借用尾部分段；
- 相同的软边界移动规则；
- 相同的 Ghost 保护门槛。

因此当前方案不是为 SWA 重新设计一套淘汰策略，而是将同一策略适配到 Full 和 SWA 的不同工程回收接口。SWA 内部的 Full/SWA 池分别统计物理状态，但使用同一个 Agent/request 分区语义。

### 9.1 参数逐项释义

| 参数 | 当前值 | 含义 | 当前候选中的作用 |
|---|---:|---|---|
| `request_cache_region_policy` | `elastic` | 选择区域容量策略。`elastic` 表示最低保障线之外的容量属于共享池 | 启用本报告描述的动态分区逻辑 |
| `request_agent_cache_ratio` | `0.50` | Agent 的初始/中性比例 | 冷启动或只有一类请求近期出现时的 50/50 返回保障，也是软边界初始位置；不是离线流量比例 |
| `request_cache_agent_min_ratio` | `0.20` | Agent 最低保障比例 | 两类都活跃时，Agent 的保护线为总容量的 20% |
| `request_cache_agent_max_ratio` | `0.80` | Agent 的软边界上限 | 同时意味着普通请求的最低保障线为 `1 - 0.80 = 0.20`；主要是回收偏好上限，不是绝对物理占用上限 |
| `request_cache_elastic_activity_window` | `32` | 判断一侧是否近期活跃的在线访问窗口大小 | 使用最近 32 个缓存访问事件判断是否进入两侧 20% 保障模式；窗口内只有一侧时暂时使用 50/50 保障 |
| `request_cache_elastic_preferred_reclaim` | `true` | 是否先回收超过软边界的 preferred borrowed 节点 | 开启后分两级回收；先处理 preferred borrowed，再处理普通 borrowed |
| `request_cache_elastic_soft_step` | `0.10` | 软边界单次最大移动幅度 | 每次最多移动 10 个百分点，减少驻留 mix 短暂变化造成的抖动；`1.0` 表示立即跟随 |
| `request_cache_borrowed_segment_tokens` | `1024` | 借用尾部单个 Radix 段的目标上限 | 只切分跨过保障线的尾部；当前 page 为 256，因此 1024 token 等于 4 个 page |
| `request_cache_elastic_ghost_capacity_tokens` | `1,048,576` | Ghost 元数据预算 | 最多保存约 1M token 对应的 page 指纹和分数，不保存 KV tensor；设为 0 会关闭 Ghost |
| `request_cache_elastic_ghost_pressure_decay` | `0.995` | Ghost 回访压力的每请求衰减系数 | 每个新的请求事件将旧压力乘以 0.995；按请求次数衰减，不按墙钟时间衰减 |
| `request_cache_elastic_ghost_protect` | `true` | 是否保护已证明会导致重算的借用节点 | 开启后高分节点只在 borrowed reclaim 中延后回收，不影响普通区域 LRU |
| `request_cache_elastic_ghost_protect_min_tokens` | `1024` | 触发 Ghost 保护所需的最小衰减后重算分数 | 至少积累 1024 个重算 token 才保护；设为 0 时实际门槛为一个 page |
| `request_cache_elastic_ghost_reclaim` | `false` | 是否让 Ghost 压力改变跨区域回收顺序 | 当前关闭，因此仍使用固定的 `request_first`；开启后才会根据两侧 Ghost 压力选择先回收哪一侧 |
| `request_cache_elastic_ghost_bias` | `0` | Ghost 压力对软 Agent 比例的偏置强度 | 当前为 0，不改变软比例；Ghost 只做节点级保护 |
| `request_cache_elastic_feedback` | `false` | 是否根据实际 borrowed 驱逐压力调整基础返回比例 | 当前关闭，因此不会持续追踪驱逐量修改 50/50 基础线；只使用共享池和软回收边界 |
| `page_size` | `256` | 缓存物理 page 的 token 粒度 | 控制前缀匹配、尾部分段、Ghost 指纹和驱逐的对齐单位，不是额外容量 |

当前还隐含使用：

```text
request_cache_elastic_reclaim_order = request_first
request_cache_elastic_activity_requires_hit = false
```

`request_first` 表示共享池压力下先处理普通请求的借用节点，以尽量保护 Agent 的长链历史。`activity_requires_hit=false` 表示只要观察到该区域的在线缓存访问，就可以刷新活动状态；如果改为 `true`，只有实际发生 prefix/host hit 才算近期活跃。

代码中还有一组 `request_cache_ratio_*` 比例反馈参数，例如 `alpha`、最大步长、压力滞后和驱逐 token 门槛。它们只在 `request_cache_elastic_feedback=true` 或其他动态比例策略启用时参与控制；当前候选中不会改变结果。

## 10. 当前实验依据

工作负载为 `experiments/动态分区试验/data/bidirectional_reuse_short_phased_20261001`，包含混合请求、7 个 Agent session 并行压力和普通请求回访。

三次有效的 1024-token + Ghost 复核结果：

| 配置 | 总体命中率 | Agent 命中率 | 普通请求命中率 | 额外重算 token |
|---|---:|---:|---:|---:|
| 无 Ghost，2048 分段 | 46.0181% | 45.8093% | 77.2283% | 4,024,320 |
| Ghost，2048 分段 | 52.0327% | 51.8642% | 77.2283% | 3,531,008 |
| **Ghost，1024 分段** | **54.6959%** | **54.5452%** | **77.2283%** | **3,311,445** |

相对无 Ghost 的 2048-token 分段基线，当前候选：

- 总体命中率提高 **8.678 个百分点**；
- 额外重算减少 **17.71%**；
- 普通请求命中率没有下降。

相比 Ghost + 2048-token 分段，1024-token 分段进一步减少约 **6.22%** 的额外重算，但 TTFT p50 增加约 **3.3%**，墙钟时间增加约 **1.9%**。

完整结果见：

- [`dynamic_partition_ghost_protection_20261005.md`](dynamic_partition_ghost_protection_20261005.md)
- [`dynamic_partition_ghost_protection_20261005.json`](dynamic_partition_ghost_protection_20261005.json)

这些结果支持把“20% 最低保障 + 共享弹性池 + 1024-token 借用尾部分段 + bounded Ghost 保护”作为下一阶段候选，但当前 workload 较短，不能把这些数字直接解释为所有混合 Agent 流量上的通用提升。后续仍需要在更长时间、更高压力和不同 Agent/request 比例下复核。

## 11. 方法边界

当前方法明确不做以下事情：

- 不预测工具调用或 turn 返回时间；
- 不使用离线流量比例决定在线分区；
- 不根据请求完成数固定触发分区变化；
- 不在 Full 和 SWA 上使用两套不同策略；
- 不用 Ghost 代替正常缓存淘汰；
- 不把历史回访标签直接当成在线可见信息。

当前方法的核心是：

> 给两类请求保留返回空间，让活跃请求使用暂时空闲的容量；出现压力时优先释放借用尾部，并根据已经发生的真实重算保护确实有价值的历史。
