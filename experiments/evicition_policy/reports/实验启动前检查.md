## 2. 最直接的阻塞：默认加载的不是本次需要的引擎

当前 Python 实际导入：

```text
/sgl-workspace/sglang/python/sglang/__init__.py
commit: f218234e4f19323d09f10c03505a89a82d52ebd4
package version: 0.0.0.dev1+gf218234e4
```

该目录跟踪文件状态干净，但本次读取其源码发现：

- 模型/配置目录中没有 `DeepseekV4` / `deepseek_v4` 实现。
- `evict_policy.py` 有 LRU/LFU，但没有 SLRU/TLRU。
- 当前服务参数中基本 radix 选择为 LRU/LFU。
- 不存在本次需要核对的 `unified_radix_cache.py`。

旧共享虚拟环境直接查询也指向同一旧源码。之前固定分区实验的包装器之所以能使用不同实现，是 `../固定分区试验对比/scripts/sglang_venv.sh` 第 13 行主动把项目 `Engine/sglang/python` 加入了 `PYTHONPATH`。本次不能继续复用该包装器，否则会回到有自研改动的引擎。

因此，既不能直接调用当前默认 `python -m sglang.launch_server`，也不能为了让 V4 启动就沿用旧包装器。需要在本实验 `runtime/` 下固定支持 V4 的官方版本，再验证策略和实际缓存后端。

本轮当前节点直连 GitHub API / raw GitHub 探测超时，没有将任何未经获取的上游 commit 标成已安装、已锁定。这里只判定当前本机环境不足，不据此判断最新官方版本不支持。

## 3. 时间检查：大部分证据良好，但不能仅凭无时区就否定或放行

全部 5,348 个请求都有请求时间、响应时间与 `duration_ms`。记录中的请求—响应时间差与 `duration_ms` 的最大绝对差仅约 **0.000237 毫秒**。相邻请求共 5,240 条候选依赖边，无缺失或负值。

候选的“上轮响应时间到下轮请求时间”分布：

| 统计 | 秒 |
|---|---:|
| 最小 | 0.022049 |
| 中位数 | 0.207637 |
| p95 | 20.802793 |
| p99 | 164.213492 |
| 最大 | 3,601.931526 |

其中 204 条间隔超过 30 秒。本次没有裁剪或改写这些值。

无时区的同一时钟差值可以用于相对间隔，**“未注明时区”本身不是数据失效的充分条件**。尚需确认响应时间是完整响应结束、而非响应头或首 token；耗时字段也可能与同一时间点一起生成，数值一致不是独立的结束语义证明。源请求全部标记 `stream=false`、响应体有完整 choices 和 usage，是有利证据，但仍应与采集器对应版本核对。

本次下载的数据卡将 `llm_trajectory.jsonl` 描述为可用时保存的提供商级 LLM 轨迹，但未给出这批文件时间字段的精确采集位置。不能仅凭数据卡和数值一致性就宣称采集器结束语义已经验证。

## 4. 编码检查发现：不能默用旧 chat 模式或源 token 数

本次完整检查 5,348 个原始请求：

- 请求字段均为 `model`、`messages`、`input`、`tools`、`stream`，其中 `input == messages`。
- 请求体没有显式 `thinking`、`reasoning_effort` 或 `chat_template_kwargs`。
- 所有记录中的输入消息均没有 `reasoning_content` 字段，但 5,179 个响应含 reasoning 内容。这是原始文件的现象，不是本次规范化过程删除所致。
- 发布配置元数据称最大推理强度，但抽查的运行配置 `reasoning_effort` 为 null；仅靠名称不能还原提供商侧默认值或代理注入行为。

采用权重目录自带 `encoding/encoding_dsv4.py` 与 `tokenizer.json`，对每条轨迹的首轮和源 usage 输入最长的一轮，共 **216 个不同请求**，检查三个候选模式。只按明确规则把请求 tools 挂到已有 system message；不补写原始消息中缺失的 reasoning，不执行工具。

| 候选编码 | 成功 / 样本 | 与源 prompt usage 长度完全相同 | 本地长度减源长度范围 |
|---|---:|---:|---:|
| chat，无 effort | 216 / 216 | 0 | -41,549 ～ +196 |
| thinking，无 effort | 216 / 216 | 0 | -41,385 ～ +196 |
| thinking，max effort | 216 / 216 | 0 | -41,306 ～ +275 |

候选输入加源输出长度在这些样本中没有超出模型配置的 1,048,576 token 上限。**这不是全量输入长度准入，也不是实际服务 token 一致性验证。** 源 usage 输入最大值为 209,220，输出最大值为 11,261；这些仍是来源服务的统计，不能当本次服务观测。

长度差异本身不能证明文件损坏，也不能推出一定缺失了多少内容；不同提供商模板、模型版本、工具处理与统计语义都有可能。必须先确定本次明确的模板及 thinking 规则，再核对本地编码与所选官方服务实际接收 token 一致。若无法还原来源模板，应称为“固定目标编码的历史内容回放”，披露偏差；不能要求凑齐源 token 数而改写原始请求或挑选差异小的样本。

记录中的 269 条相邻消息序列不是完整追加，涉及 50 条轨迹；不能全部称为压缩，也不能删掉。后续要区分真实编辑、压缩、工具消息处理与其他变换。

## 5. 时间预算与外推边界

评估候选集存在单次间隔约 60 分钟的轨迹；一条完整轨迹累计等待约 **72.1 分钟**，源记录请求耗时加等待约 **79.2 分钟**。如果保留这条完整会话，每轮完成时间仅等待部分就不可能保证在 30–60 分钟内；本地推理速度和合成启动偏移还会改变总时长。不能为了符合旧预算把等待截断。

校准集最大单次等待约 16.7 分钟，最长累计等待约 33.4 分钟；预跑也不能预设只有几分钟。正式会话范围、启动密度和总排期需要结合校准结果确定，而不是事后按策略收益选样本。

另外，源 metadata 明确记载上传条目经过健康状态审查；本批结果元数据均无 task error、非 partial，这是上游选择后的数据，不是无筛选生产流量。我们本次没有再按奖励或缓存复用率筛选，但不能据此数据推断所有失败、中断或其他 Agent 框架的分布。

1. 安装本实验独立官方引擎并固定 commit、依赖、实际导入路径；不修改旧项目引擎。
2. 确认采集时间语义，冻结目标编码规则，完成全量编码与上下文准入。
3. 实现无分类/无分区参数的回放器、逐请求记录、重启和中断保存；完善测试。
4. 仅用校准集做小规模 GPU 预跑，核验模型、后端、Full/SWA 策略路径、输出长度和 CUDA Graph。
5. 冻结容量、到达计划和策略集合后，再启动正式平衡重复对照。

最终准入不能只凭“脚本能启动”或“GPU 空闲”。当前硬阻塞是隔离环境与运行链路尚未建立，以及输入编码/时间语义未放行。**本轮只报告检查结论，不启动正式实验。**
