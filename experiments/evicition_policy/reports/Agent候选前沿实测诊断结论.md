# Agent 候选前沿实测诊断结论

日期：2026-09-29  
状态：**诊断补丁、固定 trace、四组 GPU 实验和分析均已完成。**

最终有效 suite：`results/pilot/exact_diagnostics_20260929T054622Z/`  
机器结果：`reports/agent_candidate_runtime_diagnostics_20260929.json`

## 1. 结论

这次实验不支持“给所有新尾部一次有限二次机会”作为主策略。更值得实现的最小机制是：

> **当删除叶子后暴露父节点时，给这个刚暴露的父节点一个只在当前回收决策内有效的延迟资格，优先让回收转向其他原始候选；只有其他候选不足以完成释放时，才继续沿同一条链向上回收。**

它不是预测工具时间或下一轮返回时间，也不长期保护整条链。它只约束一次回收过程中的“连续向同一链深挖”，可以实现为 `exposure_epoch`、当前决策的 deferred queue，或每次回收的 `max_chain_descent` 上限。

同时，当前主要问题不能只靠排序解决。节点释放粒度和 SWA 池都是硬约束：

1. Full 累计只需要释放 46,592 token，却实际释放 91,648 token，超额 45,056 token，超额量相当于需求的 **96.70%**。
2. SWA 累计只需要释放 45,568 token，却实际释放 109,568 token，超额 64,000 token，超额量相当于需求的 **140.45%**。
3. 压力组后续请求几乎都只命中四条链共享的 512-token 公共前缀。相对无 Full 压力对照，23/27 个请求累计多处理 96,256 token。
4. LRU 与当前 SLRU 的 Full victim、SWA victim、逐请求命中 token 完全相同。因此本压力点不能证明 SLRU 有任何额外作用，也不能用单次延迟差给两者排名。

下一版机制应按以下顺序实现和验证：

1. **先实现“刚暴露祖先延迟进入当前候选前沿”**，保持其他节点仍按 LRU 排序，并保留资源不足时的原生回退。
2. **增加大节点的释放量惩罚或页级拆分实验**，减少为了几百 token 一次删除 3K–4K token 节点的情况。
3. **把 Full 和 SWA 分开校准**。当前 DeepSeek-V4-Flash 的 SWA 回收固定为 LRU，已经主导本压力点；只改 Full 策略很可能看不到收益。

## 2. 有效实验口径

受控 workload 包含 4 个会话、27 个请求、22 次严格续接和 1 次受控分叉。初始输入为 4,096 token；每轮逻辑增长为 32 个模型输出 token加 224 个工具追加 token，正好一页 256 token。

最终比较使用一次真实闭环运行捕获的完整输入 trace，再将相同的 `input_ids` 和请求顺序固定重放到四组实验：

| 组 | Full 容量 | SWA 容量 | Full 策略 | 采集 |
|---|---:|---:|---|---|
| control-off | 32,768 | 16,384 | LRU | 关闭 |
| control-on | 32,768 | 16,384 | LRU | 开启 |
| pressure-LRU | 16,384 | 8,192 | LRU | 开启 |
| pressure-SLRU | 16,384 | 8,192 | SLRU | 开启 |

四组输入 token trace 完全一致，所有组均完成 27 个请求；候选快照完整、回收 begin/end 配对完整，初始合法候选中没有锁定节点。采集开关开启和关闭时逐请求 cached token 完全一致，说明只读采集没有改变缓存选择。两次控制组的时间不能用于估算采集开销，因为顺序运行受到 JIT 和热缓存影响。

DeepSeek-V4-Flash 即使使用 `temperature=0`，不同服务启动的生成 token 仍不完全一致。因此第一次闭环 suite 不能用于策略公平比较，已保留为 `exact_diagnostics_20260929T052620Z`，分析结果另存为 `agent_candidate_runtime_diagnostics_20260929.closed_loop_noncomparable.json`。

最终 suite 使用固定输入重放。每个输入均页对齐，而当前运行生成长度只有 32 token，小于 256-token 页；请求结束时本轮不同的生成尾部不会形成新的完整提交页。下一轮实际提交的是固定 trace 中捕获的 32+224 token 页面。因此输出非确定性不会改变四组固定输入的缓存需求序列。

## 3. “几乎所有前缀都会复用”在真实候选上的含义

压力 LRU 的 Full 初始候选中，共观察到 72 次候选出现；它们当时都没有本诊断器记录到的精确 prefix demand。可是离线查看同一固定 trace 的未来请求后：

| 指标 | 数量 | 占比 |
|---|---:|---:|
| 尚无精确 demand 的初始候选出现次数 | 72 | 100% |
| 之后不再被需求 | 12 | 16.67% |
| 尚无精确 demand 的候选 token | 76,544 | 100% |
| 之后不再被需求的 token | 4,096 | **5.35%** |

因此，**“当前还是叶子”或“节点自己尚未被命中”不是一次性内容的可靠信号**。按 token 量看，94.65% 的这类候选仍会在后续请求中被需要。给所有节点一次机会后再保护，会很快让大多数节点获得资格，无法形成有效区分。

这与此前“最终 52 个末端页中 50 个只观察到一次需求”并不矛盾。最终末端页描述内容树结束时最外层的一页；运行时 radix leaf 可能把末端新页与数千 token 的可复用历史压缩在同一个节点中。实际回收单位不是孤立的最后一页。

日志还显示，72 次 Full 初始候选的原生 `hit_count` 为：

- `hit_count=1`：23 次；
- `hit_count=2`：49 次，占 68.06%。

当前 SLRU 的保护阈值正是 2。SGLang 在新节点插入时增加 `hit_count`，节点 split 时又把子节点计数复制给新父节点。因此 49 次候选已经进入 SLRU 的 protected 组，但诊断器没有观察到它们自身此前的精确 demand。**原生 hit_count 混合了插入、匹配和结构继承，不能直接作为“该新尾部已经被下一轮复用”的证据。**

## 4. 损失发生在哪里

### 4.1 Full：初始候选损失更大，沿链深挖也不可忽略

Full 的 22 次回收一共执行 40 个 victim step：

- 10 次回收只删 1 个节点；
- 6 次删 2 个节点；
- 6 次删 3 个节点；
- 21/22 次发生超额释放。

其中 11/22 次回收在删除叶子后继续处理刚暴露的父节点；共暴露并随后删除 17 个祖先节点，占全部 Full victim step 的 42.5%。6 次回收连续深入两层，最大暴露深度为 2。

| 回收阶段 | 释放 token | 后续再次需求 token | 再需求占比 |
|---|---:|---:|---:|
| 回收开始时已有候选 | 47,872 | 45,568 | **95.19%** |
| 删除叶子后新暴露祖先 | 43,776 | 27,904 | **63.74%** |
| 合计 | 91,648 | 73,472 | **80.17%** |

按绝对损失量看，初始候选阶段仍然更大；不能把问题全部归因于删尾后的深挖。但新暴露祖先贡献了 47.77% 的释放量，其中 27,904 token 后续再次被需求，已经足以支撑一个针对性的最小改动。

### 4.2 大节点是超额释放的直接来源

40 个 Full victim 的逻辑长度分布为：

| 节点长度 | victim 次数 |
|---:|---:|
| 256 | 13 |
| 512 | 2 |
| 768 | 2 |
| 3,328 | 3 |
| 3,584 | 4 |
| 3,840 | 16 |

57.5% 的 victim step 一次删除至少 3,328 token。多个典型回收只缺 1,280–3,328 token，却在删除 256-token 尾部后继续删除 3,840-token 父节点，最终释放 4,096–4,864 token。**若不改变释放粒度，仅调整排序很容易只是改成删除另一条同样大的链。**

### 4.3 SWA 是当前压力点的主导约束

SWA 共发生 27 次回收、70 个 step，24 次出现超额释放。被释放的 109,568 token 中，96,256 token 在后续请求中再次被需求，占 87.85%。这个数值与相对 control 的累计额外处理 token 完全相等；结合压力组从第 5 个请求开始几乎始终只命中 512 token，可以判断 SWA 容量和独立 LRU 路径是当前 cliff 的主导因素。

SWA 回收不调用 CLI 选择的 LRU/SLRU Full 评分器。因而在这个容量点，只优化 Full 的排序不足以恢复前缀命中。后续应先做两个隔离实验：

1. 固定 Full 压力，提高 SWA 容量，观察 Full 策略能否产生差异；
2. 固定 Full 容量，扫描 SWA 容量，找到从公共 512-token 命中恢复到私有链命中的临界区间。

## 5. LRU 与 SLRU 为什么完全相同

固定 trace 下，LRU 和 SLRU 的结果满足：

- 每个请求的 cached token 完全相同，累计均为 13,312；
- Full 的 22 次回收边界和 40 个 victim 完全相同；
- SWA 的 27 次回收边界和 70 个 victim 完全相同；
- 相对 control 的额外处理量均为 96,256 token。

SLRU 不是没有运行，而是在这条 trace 上没有改变顺序。其规则只有两个组：`hit_count < 2` 的 probationary 和 `hit_count >= 2` 的 protected，组内仍按 LRU。当前每次 LRU 最老的合法候选已经位于 SLRU 当时最低的可用组；等进入 `hit_count=2` 的节点时，较低组已经没有更合适候选。因此两个策略逐步退化为相同选择。

压力 LRU 与 SLRU 的平均 TTFT 分别为 0.749 秒和 0.897 秒，但缓存命中和 victim 序列完全相同。这是单次顺序启动、JIT 和系统噪声下的时间波动，不能解释为策略差异。

## 6. 建议实现的最小策略

第一版建议命名为 **LRU + Exposure Barrier**，只修改 Full 回收候选进入时机：

```text
1. 回收开始时，对已有合法候选按原生 LRU 建堆。
2. 删除叶子后，如果父节点刚成为合法候选：
   - 标记 exposure_epoch = 当前 eviction_id；
   - 先放入 deferred_exposed，而不是立即放回主堆。
3. 主堆仍有候选时，不从 deferred_exposed 取节点。
4. 主堆耗尽且仍未释放足够空间时，再按 LRU 使用 deferred_exposed。
5. 回收结束后清除临时标记；下一次回收中该父节点恢复普通资格。
```

这个机制等价于只给“刚暴露祖先”一次有界、单决策的二次机会。它不需要 session ID、任务结束信号、工具时间预测或未来访问预测，也不会让所有历史节点长期晋升。

建议同时记录并测试两个参数，但第一轮只启用一个：

- `defer_exposed_parent=true`：优先建议，参数最少；
- `max_chain_descent_per_eviction=1`：备用硬上限，在没有其他候选时可能无法一次释放足够空间，因此必须保留安全回退。

第二个独立机制是 **size-aware victim / page split**。先做诊断性实现：当候选节点大于剩余释放需求的若干倍时，提高其排序代价；如果仍确认收益，再评估显式按页拆分节点的元数据和操作开销。不要在第一版同时加入复杂父链信用、频率衰减和时间预测，否则无法判断收益来源。

## 7. 下一轮验收

当前 16K Full / 8K SWA 点已经进入严重轮转抖动，四条私有链全部退化到公共 512-token 命中，不适合作为唯一压力点。下一轮至少扫描：

```text
Full/SWA = 16K/8K, 20K/10K, 24K/12K, 28K/14K, 32K/16K
```

并增加一组“Full 容量不变、单独提高 SWA”的隔离配置。每个容量点固定同一输入 trace，比较：

- LRU；
- 原生 SLRU；
- LRU + Exposure Barrier；
- 若前两步确认粒度问题，再加入 size-aware 或页级拆分。

验收指标按优先级为：

1. 相对无压力 shadow/control 的额外处理 token；
2. 后续再次需求却被回收的 token；
3. 超额释放 token 与 `released/requested`；
4. 同一 eviction 内沿链深入次数；
5. TTFT 和请求耗时，且需要重复运行和顺序互换后再解释。

如果 Exposure Barrier 只减少沿链深入，却没有降低额外处理量，说明其他初始候选同样有高价值，应转向粒度和准入问题；如果提高 SWA 后 Full 策略才出现差异，则后续 Agent 定制策略必须同时说明两个物理池的作用边界。
