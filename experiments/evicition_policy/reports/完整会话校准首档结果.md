## 4. 两项重要观测限制

### 4.1 原生逐请求排队时间不能直接用

全部响应中的 `queue_time` 都是 0，且缺少 `forward_entry_time` / `prefill_finished_time`。这并不表示没有排队。

核对固定安装包发现：`SchedulerReqTimeStats.__getstate__` 第一次序列化只传时间戳、不传启用标记；接收对象的 `enable_metrics` 回到默认 false。经 detokenizer 再转发一次时，第二次序列化返回空状态，最终 queue_time 退化为 0。对安装包类做两轮 pickle 的 CPU 复现得到 `2.0 → 2.0 → 0.0`，未改动任何引擎文件。

证据：`results/audit/native_queue_time_serialization_20260926.json`；源码为隔离环境中的 `sglang/srt/observability/req_time_stats.py` 与 `sglang/srt/managers/detokenizer_manager.py`。该问题足以解释当前响应字段，分析脚本将其保留为原始不可信值。

改用 scheduler 原生 `queue_time_seconds` 直方图的测量前后差值，各 rank 单独计算，8 个 rank 的计数增量均为 **393**，与测量请求数一致。取 rank 0 展示，不相加：

- 平均排队约 **31.99 毫秒**。
- p50 位于 **1–5 毫秒**桶，p95 位于 **5–10 毫秒**桶，p99 位于 **1–2 秒**桶。
- 这是桶范围，不是精确逐请求分位数；当前无法将原生 queue_time 精确关联到具体请求做归因。

### 4.2 真实生成不等于历史回答

385 个相邻续接检查中，“上一轮完整输入加本地输出”与下一轮历史输入完整一致的次数为 **0**。此指标要求整个生成尾部精确一致，不能推导为 0% 前缀复用；本次实际命中率仍为 90.67%。

因此必须继续把输入前缀复用、生成尾部差异、历史改写和缓存淘汰分开。不能把未命中 token 全归到淘汰策略，也不能用本回放判断真实 Agent 任务质量。

## 5. 正式参数与排期建议，尚未冻结

### 容量

先保留 Full 655,360 / SWA 65,536 作为候选。理由是首档已经有回收和高驻留，同时无 OOM、无撤回、没有持续长队列迹象；不应为了放大算法差距继续盲目缩容。后续若进行容量敏感性，只在同一校准数据和到达规则下运行 LRU，不以候选策略表现选点。

### 启动密度

不建议把 8 会话的“每 15 秒启动”直接外推为 83 会话，可能让计算排队掩盖缓存策略。提出**固定哈希顺序，每 90 秒启动一个完整会话**，最大运行请求数仍为 8；所有策略共享同一个首轮时间表，不使用按策略运行速度变化的会话准入规则。原始会话内等待仍然保留。

该密度还需在校准任务上验证，并检查长输入预热。只提出候选，未创建可运行 formal manifest，也没有打开 formal gate。

### 时间预算

评估池共 2,358,155 个目标输出 token；单个最长会话仅累计等待就达 4,328.344 秒（72.1 分钟）。因此“完整覆盖且单次一小时内完成”不可保证。

`scripts/estimate_formal_budget.py` 使用校准集请求延迟总和 / 输出 token 数作为粗服务时间比例，对全部评估会话加上原始等待和固定启动偏移，**不拟合性能模型、不模拟队列、不用评估策略成绩调参**：

| 首轮启动间隔 | 粗算完成时间，按校准服务比例 | 用途 |
|---|---:|---|
| 60 秒 | 约 2.69 小时 | 较高密度候选，排队风险未验证 |
| 90 秒 | 约 3.34 小时 | 建议的折中候选 |
| 120 秒 | 约 3.99 小时 | 更保守的启动计划 |

90 秒方案将粗服务时间乘以 0.5/1/2 时，完成时间约 3.25/3.34/3.53 小时；这些不是置信区间，未建模长上下文、额外 cache miss 或过载排队，实际可能超出。完整估算输入和哈希见 `results/analysis/formal_budget_proposal_20260926.json`。
