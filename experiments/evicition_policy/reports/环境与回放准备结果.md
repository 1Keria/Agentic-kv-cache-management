## 2. 原生策略的准确比较范围

实际后端是 Python `UnifiedRadixCache`，环境变量固定为 `SGLANG_ENABLE_UNIFIED_RADIX_TREE=1`、`SGLANG_EXPERIMENTAL_CPP_RADIX_TREE=0`。

| 项目 | 所选版本的实际行为 |
|---|---|
| Full 侧触发回收 | `FullComponent.drive_eviction` 调用选中策略的 `get_priority` |
| LRU | 按 `last_access_time` 排序 |
| LFU | 按 `(hit_count, last_access_time)` 排序 |
| SLRU | 默认 `hit_count >= 2` 进入保护组；先回收未保护组，组内按时间排序；不是带固定段容量配额的实现 |
| SWA 侧额外回收 | `SWAComponent.drive_eviction` 从独立 LRU 链表挑未锁定节点，不调用 CLI 选择的评分器 |
| 双池联动 | 某些叶节点移除会同时释放组件；不能把两个池理解成完全独立 |
| TLRU | 锁定发行版中不存在，未运行；不移植实现来冒充原生支持 |

因此对照名称应为“**原生 Unified 后端下 Full 回收策略对照，SWA 独立回收保持 LRU**”，不能称为“两个池同时切换 LRU/LFU/SLRU”。如果压力主要来自 SWA，Full 排序差异可能被掩盖；需在之后的容量校准和观测中识别，当前不据此宣布某策略无效。

CPU 测试直接调用安装包里的 Full/SWA 回收驱动，检查策略排序、父节点进入候选集合、SLRU 门槛及 SWA 不调用评分器。它们不是完整 GPU 压力场景，也不证明已经获得逐次淘汰候选集合。

## 3. 输入协议：固定目标编码，不伪造历史提供商

编码使用所选 SGLang 自己的 `ChatCompletionRequest` 与 `OpenAIServingChat._apply_jinja_template`，固定 `thinking=true`、`reasoning_effort=max`。原始 messages 和 tools 保留；只去掉与 messages 完全重复的 input 字段，不添加输入中本来没有的 reasoning。

此规则是本轮明确的目标编码选择，不是已证明的历史 provider wire 模板。metadata 提到最大推理强度，但原始请求缺少明确 thinking/effort，源 usage 与目标编码长度不同。不能改写输入去凑源 token 数。

在线验证包括：

1. 抽取固定校准样本，调用在线 `/tokenize`，逐个 token ID 与编码文件精确比较，而不只比较长度。
2. 该版 `TokenizeRequest` 顶层不接受 `reasoning_effort=max`，因此依赖已锁定的服务环境 `SGLANG_DSV4_REASONING_EFFORT=max`；不是把 max 静默改成 high。
3. `/generate` 传入固定 input_ids，用非流式 `return_prompt_token_ids` 验证服务输入逐 ID 一致；正式回放流式请求不重复返回大段 prompt。

回放输入不带会话身份、类别、分区、cache salt 或自定义评分字段。会话 ID 仅用于客户端调度和本地记录。

## 4. 生成与会话依赖

- 使用 `/generate` 原生流式接口；temperature=0、sampling_seed=42、ignore_eos=true。
- 完整回放以源 `completion_tokens` 为输出长度目标。这是控制生成工作量的实验约束，不声称本次生成等于历史回答。
- 每次核对真实 output_ids 长度、原生 completion_tokens、prompt_tokens 和 length 结束原因；错误、截断、缺少完成标记均使运行失败。
- 首 token 时间来自第一次收到实际 output_ids，不把空文本或 usage 块计入。保留逐块时间和 delta token IDs；这是客户端接收时间，不是 GPU 内核时刻。
- 每个会话下一轮等待：**本地上轮完成 + 原始记录间隔**。不把长等待封顶，不将缺失值置零。跨会话首轮偏移显式指定并冻结，标为合成启动计划。
- 下一轮继续使用历史输入，不将本次生成拼回历史。保存“上轮本地输入+输出”与下轮历史输入的最长公共前缀及完整续接是否一致，暴露生成偏差。
- 当前烟测只用按 session_id 排序的前两个校准会话、各前两轮，每轮输出最多 32 token。此截断只允许 smoke 模式，不是正式数据规模选择，不作为性能排名证据。

## 7. 运行编排与结果保存

`run_suite.sh` 默认只执行三策略烟测；服务严格串行，切换策略先停止再重启。每次运行创建唯一目录，拒绝覆盖，检查端口和 GPU 计算进程，绝不接管或杀掉未知服务。

每次流程：启动 → 读取实际后端/容量/图 → 在线编码核验 → 固定烟测预热 → 官方 flush → 等待原生空闲/空缓存指标 → 回放 → 保存末态 → 停止本次进程并核对端口退出。

首次三策略烟测暴露两项工程问题，未删除记录：

- `/flush_cache` 成功不代表 `/metrics` 的 gauge 已立即更新。该版本空闲指标约 30 秒刷新一次。新版编排等待 running/queued、Full used/evictable、SWA evictable 全为零，再开始测量；不会把缺失指标视作零。
- 直接给整个进程组发 SIGTERM 会触发官方子进程故障告警。新版先向服务父进程发 SIGTERM，让官方排空并清理；超时才升级到仅本次拥有的进程组。官方退出自身会调用 kill_process_tree，退出码需结合主动停止记录解读。
- 第二批预跑在 LRU 完成后，Linux 进程已退出，但 GPU 驱动还短暂列出旧 PID 和显存。安全检查拒绝启动 LFU，批次标记 failed。新版在退出时等待本次拥有的 GPU PID 消失，仍不放宽对外部占用的检查；最终三策略顺序复测通过。

结果保存在 `results/pilot/<唯一批次>/<序号>_<策略>/`：命令、配置、脚本指纹、PID、server.log、在线编码证据、预热和测量请求/事件、清缓存响应、前后原生 metrics、GPU 采样、实际容量签名、状态及 cleanup。

监控中的原生 gauge 不是严格实时，也不重复累计 TP 副本；客户端请求日志优先用于完成数与延迟。没有得到 Full/SWA 完整淘汰事件或合法候选集，不做精确错误淘汰归因。
