**我赞成，而且这很适合作为你现在的下一步。** 先用 Agent-only 流量，在固定容量下研究复用规律和驱逐行为，能让你清楚地判断：Agent 区内部究竟有没有值得优化的问题，以及新机制应该解决什么。

这组实验主要支撑“Agent 区策略为什么有效”；后面仍需要回到混合流量，验证它与分区机制组合后的系统收益。我建议把这一阶段做成下面这条链：

**刻画请求行为 → 比较已有策略 → 定位主要损失 → 验证一个最小改动。**

**首先，把实验边界固定下来。**

只用 Agent 请求，但保留多个 Agent、多 session 和不同任务类型。分类器、动态配额、跨区借用可以暂时关闭。

容量尤其需要控制：**仍然给 Agent 区设置明确的缓存预算，不要因为移除了普通请求，就让 Agent 使用原来整个共享池的容量。** 建议扫描几个相同的容量点，从基本没有竞争，到中等压力，再到明显不足；每个容量点，各策略使用同样的资源配置。

同时记录活跃 KV 和可驱逐 KV。SGLang 的候选集受到叶节点和引用锁约束，因此一次回收困难可能来自活跃请求占用，也可能来自驱逐选择，需要分开解释。([raw.githubusercontent.com](https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/mem_cache/radix_cache.py))

**然后，优先刻画下面五种行为，而不只是输入、输出长度。**

| 要观察的行为 | 建议记录什么 | 它帮助你回答什么 |
|---|---|---|
| **真实前缀延续** | 下一轮输入与上一轮上下文实际匹配的 token 数、历史压缩或改写位置 | 看起来是同一 session，是否真的可以复用 KV？ |
| **两次复用之间的竞争** | 等待秒数，以及期间其他请求访问、产生的去重 KV 字节量 | 淘汰与绝对等待时间、竞争流量分别有什么关系？ |
| **上下文增长** | 每轮新增长度；新增尾部在之后是否复用；此前已发生多少次续接 | 旧上下文的复用证据是否对新尾部有价值？ |
| **共享结构** | 公共前缀、私有历史、分叉部分的物理字节量与访问情况 | 收益来自跨 session 共享，还是同一链的续接？ |
| **生命周期** | 首次调用、已续接、分叉、结束、取消；明确哪些事件服务端可见 | 哪些信息可以成为线上策略依据？ |

这里要按**实际 token 前缀和缓存命名空间**统计，而不是按语义相似或 session ID 推断。SGLang 的前缀匹配由这些条件决定，还受页对齐影响。([raw.githubusercontent.com](https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/mem_cache/radix_cache.py))

另外，trace 结束时没有观察到回访的 session，建议标成“后续未知”；不要全部算成一次性任务，否则会低估长间隔复用。

**第一轮策略对照，我建议以 LRU、LFU、SLRU 为主。**

我核对的 SGLang 当前源码中：

- LRU 按节点最后访问时间排序；
- LFU 按节点命中次数、再按时间排序；
- SLRU 按命中次数阈值划分优先级，再在组内按时间排序。

尤其需要注明：这里的 SLRU 实现没有独立的保护段容量控制，不能直接把它等同于所有经典 SLRU 实现。实验应固定代码 commit，写清参数和具体规则。([raw.githubusercontent.com](https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/mem_cache/evict_policy.py))

TLRU 可以随后加入，尤其当你发现主要问题与上下文长度、尾部 TTFT 有关时。它的目标包含尾延迟优化，所以对比时也要报告相应指标，不能只凭平均命中率给它排名。([arxiv.org](https://arxiv.org/abs/2510.15152?utm_source=openai))

对这些策略，你可以预先列出**待检验假设**：

| 策略 | 值得检验的失效假设 | 怎样才算有证据 |
|---|---|---|
| LRU | 一批新到达的 Agent 上下文，挤掉了此前已多次续接的上下文 | 相同容量下，利用既有续接证据调整选择，能减少总重算 |
| LFU | 历史高频、近期已不再复用的分支占用容量 | 它排挤的其他内容具有更高的后续复用收益，且净损失显著 |
| 节点级 SLRU | 已经反复续接的链，其新增尾部仍缺乏自身命中记录 | 增加有限的资格迁移后，收益超过提前驱逐其他内容的代价 |
| 多种策略共同出现 | 单个大上下文、共享祖先或回收粒度主导了损失 | 改变排序帮助很小，而改变准入或回收粒度有明显效果 |

**这些是实验问题，不应提前写成论文结论。** 特别是我们之前讨论的“续接资格迁移”，也应该接受同样的检验，不能只寻找有利于它的案例。

**最值得先加的一项统计，是把“新增计算”和“缓存丢失导致的重算”分开。**

我建议维护一个只保存元数据的、无限保留历史前缀的影子索引。对同一条固定 trace，在请求 \(r\) 到达时记录：

- \(h_r^{\infty}\)：如果此前可缓存的历史都没有被容量淘汰，能够匹配多少 token；
- \(h_r\)：当前策略实际命中了多少 token。

定义诊断量：

\[
R_r=\max(0,h_r^{\infty}-h_r)
\]

它表示**由于没有保住已有缓存而额外处理的 token 数**。影子索引应使用相同的插入时机、匹配规则和缓存命名空间。

例如，一个请求有 20K 输入，其中过去实际出现过的可复用前缀是 16K，当前只命中 10K。那么需要重点分析的是损失的 6K，而不是把全部 10K 未命中输入都归咎于驱逐策略。

这是我建议的诊断口径。它帮助区分新工具结果带来的必要计算与容量淘汰带来的额外计算；之后还应结合实际 prefill 耗时，判断这些 token 损失究竟有多贵。它也不是一个满足有限容量约束的最优算法。

**具体实验建议分成两层。**

第一层做**相同 trace、相同预算的策略重放**。固定请求内容和事件顺序，比较缓存选择，便于解释某条上下文为什么被删、删掉后产生了什么损失。涉及节点分裂、锁定和完成插入的事件也要保留，避免模拟器与实际缓存行为不同。

第二层做**闭环 Agent serving**。下一轮应在上一轮实际完成并经过工具执行后才产生；这样能够验证缓存加速改变请求交错后，收益是否仍成立。Agent 的 LLM 调用与工具调用交替、工具等待打断 KV 复用，也是现有 Agent serving 工作明确研究的问题。([arxiv.org](https://arxiv.org/abs/2511.02230))

这两层用途不同：固定重放方便定位原因，闭环实验负责验证最终性能。闭环对照中固定任务集合、初始任务到达过程和工具延迟设定，不要求各策略产生完全相同的后续请求时间戳。

**第一轮先产出三张图，就足够决定下一步往哪里做。**

1. **容量—额外重算曲线。**  
   横轴是缓存预算，纵轴是上述额外重算 token 数或成本；对比 LRU、LFU、SLRU。先确认策略差距存在于哪些容量范围。

2. **重算损失的分桶图。**  
   分别按历史续接次数、等待期间竞争字节量、新增上下文长度分桶。关注每组贡献了多少总损失，而不仅是哪个组命中率低。

3. **一个典型驱逐时刻的时间线。**  
   展示当时合法候选、策略排序、实际释放字节、之后的回访，以及另一种选择带来的净收益。**被删除的节点后来又访问了一次，不足以证明原策略错误；还要计算为保留它而淘汰其他内容的损失。**

这些结果会给出比较清晰的决策：

- 若某类损失占比高，而且当时就有可观察信号能够区分候选，就围绕它设计一个最小机制。
- 若 SLRU 已解决大部分问题，就把它作为强基础，继续检查共享、增长或配额方面是否还有独立收益。
- 若各策略都接近，就先检查精确复用是否充分、容量压力是否合适，以及损失是否主要来自不可避免的新内容。

还有一篇相关工作建议现在记入清单：**SAECache** 已提出任务相关多队列、不同 token 类型的复用价值，以及驱逐反馈学习。这与“分类后使用不同策略”的方向比较接近，后续确定机制时需要认真区分；当前可以先完成上述基础诊断。([arxiv.org](https://arxiv.org/abs/2605.18825))

你现在最值得实现的是**统一的请求与驱逐事件日志，以及区分新增计算和重算的统计口径**。它们会让后续每一种策略改动都有可解释、可复查的依据。
